## Objective
Let an e-commerce client's store push orders into PG-EOS without a bespoke build per client: one connector layer that normalises an incoming store order into the minimum order fields, queues it, retries it under the declared failure policy, and surfaces every failure in the existing integration monitor.

## Source D-blueprint (binding for screens, boards and KPIs)
`docs/package/D-blueprints/11-Client-Store-Integration.md` — §2 what the package already promises (`I-09`) and the matching state in the database · §3 what a store client actually asks for · §4 the three options (أ API-only · ب fast bridge · ج the `I-12` connector layer) with their comparison table · §5 the proposed design for option ج including §5-2 the minimum imported-order fields, §5-3 error handling on the existing queue, §5-4 the minimum schema additions and §5-5 the nine-field failure policy · §7 the decisions the GM owes.

## Schema already present in 13B?
**Partly.** The generic integration frame is present and is the backbone the blueprint builds on: `platform.integration_config` (with `direction`, `transport`, `idempotency_key`, `retry_max`, `retry_backoff_sec`, `on_failure`, `alert_after_failures`, `alert_roles`, `raw_retention_days`, `manual_fallback`), `platform.integration_queue`, `platform.integration_runs`. **No per-store connector table exists.** Option ج needs the minimum additions listed in D-11 §5-4, which are a G-01 schema-change request the Master files after the GM picks an option — not something this task may invent.

## Acceptance criterion
A store order posted by the test connector appears as one PG-EOS order with the D-11 §5-2 minimum fields populated, is idempotent under replay (the same external id posted twice yields one order), a forced failure follows the nine-field policy of D-11 §5-5 and shows in the integration monitor with its retry count, and client isolation holds (G14: direct id substitution returns zero rows).
