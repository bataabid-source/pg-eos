## THE ONE HARD CONSTRAINT — RLS has no teeth as superuser
`PGUSER` defaults to `postgres`, a superuser, which bypasses RLS unconditionally (already documented as
a KNOWN GAP in packages/db/src/client.ts). `force row level security` binds only the table OWNER, never a
superuser. `database/schema/**` and `database/migrations/**` contain zero `create role`.

Therefore the test MUST provision its own ephemeral, non-superuser, `NOBYPASSRLS` login role in its own
setup and drop it in teardown. That is test-fixture code under `tests/`, not schema — it invents no
production role name and no production GRANT policy (that is deployment work, 0.5/0.6, still open).

Role: fixed name `pgeos_rls_isolation_test`, password generated at runtime with `randomUUID()` (never
committed; the local pg_hba is `trust` anyway, the password is only so the fixture still works on a
scram host). Setup, from a SUPERUSER `pg.Client` (separate from withContext's pool):
  1. terminate its backends, `drop owned by`, `drop role if exists`
  2. `create role pgeos_rls_isolation_test login nobypassrls password '<rand>'`
  3. `grant usage on schema sales, wms, tms, billing to <role>`
  4. `grant select on sales.accounts, wms.outbound_orders, wms.skus, tms.delivery_tasks,
     billing.invoices to <role>`  — SELECT only; the criterion is a read-side criterion.
Teardown reverses it (terminate backends first — the withContext pool is NOT exported from
`@pg-eos/db`, only `withContext` and `db` are, so you cannot call `pool.end()`; terminate via the
superuser client with `pg_terminate_backend`).

## Using withContext — ordering matters
`packages/db/src/client.ts` builds its `Pool` at MODULE LOAD from `process.env['PGUSER']`. So the test
file must, at top level and in this order:
  1. `process.env['PGUSER'] = ROLE; process.env['PGPASSWORD'] = <rand>;`
  2. `const { withContext } = await import('@pg-eos/db');`   ← dynamic, after step 1
The pool connects lazily (first `pool.connect()` inside withContext), so creating the role in
`beforeAll` is still in time.

Every scoped query in the test goes through `withContext(ctx, tx => tx.execute(...))`. Nothing else.
Seeding and cleanup go through the superuser client (they need to bypass RLS to write).

## Scenarios the file must cover (Gherkin first, in tests/isolation/client-isolation.feature)
1. **Guard-of-the-guard (must run FIRST — otherwise every later assertion is vacuous).** Inside
   `withContext`, assert `current_user` = the test role, `usesuper` = false, and
   `pg_roles.rolbypassrls` = false. If this fails the whole suite is meaningless.
2. **G7 = 0.** Run doc 40's G7 query verbatim (guards.sql:80-85 / doc 40:637) and assert `0`.
3. **Positive control, per table (5 assertions).** Client A's portal ctx
   (`{ userId: <A's portal user or null>, clientId: A, isInternal: false }`) selecting A's own row by id
   returns exactly 1 row. Without this, "0 rows" proves nothing.
4. **ID tampering, per table (5 assertions).** The SAME ctx, same query, with B's id substituted,
   returns **0 rows and throws nothing**. Assert both: zero rows AND that the promise resolved.
5. **Symmetry.** Repeat 3+4 with the roles swapped (B's ctx against A's ids) on at least
   `billing.invoices` and `wms.skus`, so the result is not an artifact of insert order.
6. **`entity_scope` does not leak.** `wms.outbound_orders`, `tms.delivery_tasks` and `billing.invoices`
   carry BOTH `entity_scope` (FOR ALL) and `client_portal_scope` (FOR SELECT), and permissive policies
   are **OR-ed**. Assert `platform.allowed_entities()` returns an empty array inside A's portal ctx (A's
   user has no `identity.user_entities` rows), which is why the OR does not defeat the client scope.
   State this in a comment — it is the non-obvious part of the proof.
   **Round-2 correction:** this scenario, as written above, proves only that the OR-leg is inert for
   a context whose `userId` has no `user_entities` row. It does NOT prove the policies compose
   safely. They do not — see "Outcome" below (SCR-RLS-01). Treat scenario 6 as a statement of the
   precondition under which scenarios 3-5 are valid, not as a proof of isolation.
7. **Internal context still sees both.** `{ clientId: null, isInternal: true }` returns both A's and B's
   rows on `billing.invoices`. Proves the policy discriminates on client identity rather than
   denying everything.
8. **No-error clause, explicitly.** A dedicated assertion that the tampered SELECT rejects with nothing
   — a `permission denied` or a thrown policy error would FAIL the criterion just as a leaked row does.

Two G-01 schema-change requests were raised, both OPEN, both reproduced against the live schema:

   wms.occupancy_snapshots · wms.space_allocations · wms.space_reservations · wms.work_orders`.

2. **SCR-RLS-02** (`docs/notes/SCR-RLS-02-audit-log-partitioned-parent-has-no-rls.md`) —
   `platform.audit_log`'s partitioned parent has `relrowsecurity = false` and no policy, so reads
   through it bypass every partition's `entity_scope`. Reproduced: a `NOBYPASSRLS` role with
   `allowed_entities() = {}` read all 8 rows, all of which carry a non-null `entity_id`. G7's
   `relkind = 'r'` filter cannot see a `relkind = 'p'` parent, so `G7 = 0` does not cover it.
   Not pinned by a test — a deliberate omission, reasoned in §6 of that note.
