## Defaults (D1-D11, batched to the GM/Master where noted)
- **D1** `ScheduleInbound` is a NEW command in a NEW use-case folder (`schedule-inbound`), roles `WH_MGR`/`WH_SUP`, legal in `draft` and `approved` (self-transition — no machine state change, version bump only, same "no machine, INSERT/UPDATE-only" shape as 2.15's manage-space commands since this is a fact-on-the-order, not a status transition). Input `expectedAt` (must be in the future — `deps.clock.now()` compared, never `new Date()`), optional `dockCode`, `scheduleNote` (audit/event payload only — no `schedule_note` column, pre-migration review finding 2), and the four logistics terms (`handoverPoint`, `transportBy`, `vehicleType`, `labourBy`, `labourCount`) all caller-supplied (D6). Writes `expected_at`, `scheduled_by`, `scheduled_at`, `dock_code`, the four logistics-term columns; emits `wms.inbound.scheduled` + one audit row, same transaction (audit `newValue` includes `scheduleNote` even though it has no column). Rescheduling = calling it again (version bump, audit trail carries history — no separate "reschedule" command).
- **D2** `ApproveInbound` gains optional `expectedAt` (+ the four logistics terms, all optional). When `expectedAt` is present: writes the same columns as D1 in addition to the status transition, and emits `wms.inbound.scheduled` IN ADDITION to `wms.inbound.approved` (two outbox rows, one transaction). When absent: status transition only, with no schedule columns and no `wms.inbound.scheduled`. `wms.inbound.approved` is written to `platform.outbox` on EVERY successful `ApproveInbound`, unconditionally, in the same transaction as the draft → approved change (Master ruling on round-2 finding 8: `packages/events/catalog.ts` "written once per ApproveInbound (draft → approved)" governs; doc 40 §B3).

## Scenario (Gherkin outline — pg-tester writes the full `.feature`)
- `ScheduleInbound` with a future `expectedAt` on a `draft` order → 200, `expected_at`/`scheduled_by`/`scheduled_at` set, version bumped, one `wms.inbound.scheduled` outbox row, one audit row, same transaction.
- `ScheduleInbound` with a past `expectedAt` → 422 (`ScheduleInPastError` or similar), nothing written.
- Rescheduling (calling `ScheduleInbound` again on an already-scheduled order) → version bumps again, a SECOND `wms.inbound.scheduled` event.
- `ApproveInbound` with `expectedAt` present → both `wms.inbound.approved` and `wms.inbound.scheduled` emitted, one transaction.
- `ApproveInbound` without `expectedAt` → status transition only, plus exactly one `wms.inbound.approved` outbox row (written unconditionally, per D2) and no `wms.inbound.scheduled` — regression-tested.
- `CancelInbound` without `cancelReason` → 422, nothing written.
- `CancelInbound` with `cancelReason` → `cancel_reason` persisted, `wms.inbound.cancelled` emitted carrying it.
- `vehicle_type` outside the closed list (via either command) → 422, nothing written.
- `listScheduledAppointmentsToday`-style query returns today's appointments ordered by `expected_at`, vehicle type + labour count visible; an approved order with no appointment is excluded (or flagged, per the "بلا موعد" query note — a read-only capability, own test).
- Idempotency-Key required on all three commands (`ScheduleInbound`, extended `ApproveInbound`, extended `CancelInbound`).
- Cross-entity isolation: a caller without the order's entity gets the standard not-found convention (RLS `entity_scope`, already governs `wms.inbound_orders`, no new policy needed).
- Property tests: `isFutureTimestamp`, `isValidVehicleType`, `isNonEmptyReason` (or equivalent) on every new invariant (doc 36 §5-5).
- Audit-row assertions on any `commercial`-classified column value (`handoverPoint`/`transportBy`/`labourBy`/`labourCount`/`deliveryTaskId` in `newValue`) must expect the `platform.sanitize_audit`-masked value (`•••`), not the raw one (pre-migration review finding 1) — event payloads are unaffected, only audit rows are masked.
- Guards touched: G1 (RLS enabled — inherited, no new table), G9 (outbox/audit pairing — three new event types), G11, G14 — per the backlog doc's acceptance line.
