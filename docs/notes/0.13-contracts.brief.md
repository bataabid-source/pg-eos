## Scenario (Gherkin)

```gherkin
Feature: packages/contracts is the single source of truth for the HTTP surface

  Scenario: The OpenAPI document is generated from the Zod contracts
    Given the shared contract registry of packages/contracts
    When "pnpm --filter @pg-eos/contracts generate:openapi" runs
    Then packages/contracts/openapi/openapi.json is written
    And the document declares an openapi version of 3.1.x
    And the document validates against the official OpenAPI 3.1 schema

  Scenario: The committed document never drifts from the contracts
    Given packages/contracts/openapi/openapi.json is committed
    When the document is regenerated in memory from the registry
    Then the regenerated document is byte-identical to the committed one

  Scenario: The contract test harness runs
    Given a route contract registered in a fixture registry
    When "pnpm --filter @pg-eos/contracts test" runs
    Then the harness accepts a request and a response payload that conform to the contract
    And the harness rejects a payload that violates the contract, naming the failing path

  Scenario: A write endpoint without Idempotency-Key fails the registry guard
    Given a POST route contract registered without an Idempotency-Key header
    When the registry invariants are checked
    Then the check fails and names the offending route and method
```

## Governing rules this slice encodes (doc 40 §A4 — copied, not invented)

- Every **write** endpoint (POST · PUT · PATCH · DELETE) requires an `Idempotency-Key` header:
  **400** without it · **409** on key reuse with a different body · replay returns the prior result
  for 7 days.
- Every mutable aggregate carries `version`; a stale `UPDATE` yields **409**.
- An illegal state transition yields **422** with a message naming the allowed transitions.
- Cross-module communication is a domain event or a declared contract in `packages/contracts`.

Nothing else about any endpoint is decided here. No business route is authored in this slice —
module contracts arrive with their own WBS tasks from 0.9 on.

## Master decisions (record in CHANGELOG; none is an ADR — none changes the architecture)

| # | decision | why |
|---|---|---|
| D1 | `zod@^4.6.5` + `zod-openapi@^6.0.2` | purpose-built for Zod 4, emits **OpenAPI 3.1** directly, uses the standard `.meta({id})` rather than patching Zod's prototype as `@asteasolutions/zod-to-openapi` does |
| D2 | **`vitest@^4.1.11`, not 5.x** | `vitest@5` declares `engines.node ^22.12.0 \|\| ^24.0.0 \|\| >=26.0.0`; this machine runs **Node 25.2.1**, which that range excludes. `vitest@4` declares `^20 \|\| ^22 \|\| >=24` and accepts it. Same class of constraint as the TS 5.9.3 ceiling in 0.4 — revisit on Node 26 LTS. |
| D3 | `@seriousme/openapi-schema-validator@^2.10.0` (dev) | makes "OpenAPI spec generated" a real assertion against the official 3.1 meta-schema instead of a shape guess |
| D4 | error body = a minimal `Problem` object (`type` · `title` · `status` · `detail` · `instance`, RFC 9457 shape) | doc 40 fixes the **status codes** (400/409/422) but not the body. BOOTSTRAP-v5 §2: state one default, record it, proceed. Shared, so every module inherits one envelope. |
| D5 | `openapi/openapi.json` is **committed**, with a drift test | the emitted document is the published contract; committing it makes review and consumer diffing possible, and the drift test stops it going stale |
| D6 | no `src/` directory — files sit at `packages/contracts/<area>/` | doc 36 §1-2 layout; a `src/`-scoped tsconfig was review finding #2 in 0.4 |
