# iMile integration scenario — the station agent as the only operational link (GM request, D-147)

Written on the GM's request of 2026-09-24 ("قدم سيناريو الربط باستخدام الوكيل مع إيميل…"). Full narrative page (Arabic, timeline + flows): https://claude.ai/artifact/4nvHwpMJtvvifkBg5idnuY . This note holds what the scenario adds to or changes in the package; everything else is doc 07, doc 23 I-01/I-02, doc 40 §C8, ADR-27/28 as written.

## 1. GM directive recorded (D-147)

Verbatim: "الوكيل هو سيكون أداة الربط الأساسية ولا يوجد بدائل، يجب أن الوكيل يعمل مع نظام iMile بسلاسة وتكامل مع نظامنا لعدم تشتت الإدارة التشغيلية بين نظامين؛ يجب أن يكون نظامنا هو الواجهة ونظام iMile في الخلفية."

Applied reading (defaults, recorded):
1. **Single front.** No employee works in the iMile portal or in outside spreadsheets. The dedicated agent account is the only iMile login (doc 07 §2-1, EXEC §1.2 — unchanged). Supervisors, auditors and drivers act only in PG-EOS.
2. **"No alternatives" = no alternative operational path.** The official API request to iMile (X.6, "in progress" per D-141 Q38c) stays a *technical* path inside the agent: if granted, it is a second adapter behind the same agent interface and changes nothing in screens or processes (doc 07 §2-1 last clause). The monthly CSV export test (doc 23 I-01) stays a readiness test, never an operating mode.
3. **Email is an agent channel, not a human one.** A dedicated mailbox for the agent (IMAP) captures what iMile sends by mail — OTP on session loss, scheduled reports, notifications — and turns each into data (session renewal · `platform.documents` + reconciliation against the portal pull · a `platform.integration_queue` row with a unique reference). Unclassifiable mail → the manual queue (N-19 on backlog). Outbound mail (weekly capacity letter, negotiation letters, discrepancy reports) is generated by the system and sent through I-07 SMTP from a card the DEL_MGR approves. Nobody reads the mailbox by eye.

## 2. Automation levels per operation (doc 07 §2-2, unchanged)

| Operation | Level | Human part |
|---|---|---|
| Sorting (scan → cage/zone/driver < 1 s) | A3 | unknown shipment → waiting cage + alert |
| Dispatch plan | A2 → A3 by earned autonomy (7-check gate + 14 plans ≥ 90% unchanged; instant demotion) | supervisor edits with reasons; override until first cage handover |

00:30 agent self-test against the portal · 01:40 nightly reconciliation (rule accuracy, auditor accuracy, driver response) · 05:30 fresh detected, expected list preloaded · 05:40 plan built · 05:45 supervisor review / auto-approval when earned · 06:00 scan sorting on PDA · every 10 min pull, every 60 s push all day · DTL engine within 1 minute of each problem · 16:00 N5 to drivers · 21:30 daily inventory (frozen In-Hub snapshot → full scan → double match → recount → explanation) · weekly capacity letter to iMile.

## 5. Clarification D-148 — two account kinds, one agent per auditor

- **Station account** = the shipment-operations-manager account. One station agent uses it for **reading** everything (shipments, statuses, audit data) every 10 minutes (I-01).
- **Audit accounts** = one iMile account per delivery-team manager. iMile tracks every audit decision by the user who made it, so there is **one agent session per auditor**, logging in with the auditor's own iMile account and executing that auditor's decisions by proxy every 60 seconds (I-02). Auditors never log in manually (single-session rule per account). Credentials: entered once by the auditor into the secrets store; OTP renewal from the auditor's mailbox through the agent's mail channel.
- **Engine decisions (ADR-27 auto-close):** pushed through the session of the auditor who owns the driver's team; our side records `closed_by = 'engine'` and the pushing user — default taken, GM may change.
- **New carrier (G-01 with 3.14/3.17):** `imile.auditor_accounts` — `employee_id`, iMile username, session state, last login, health, `is_active`; no secret stored in the row.
- Supersedes: doc 07 §2-1 "one dedicated account", doc 40 §C8 "dedicated iMile account; single session", doc 23 I-01/I-02 account column — documentary corrections queued for the Phase-3 brief.

## 6. Driver app — replacement of the iMile driver app?

**Not as a replacement, in practice.** Delivery scans and POD for iMile shipments must land in iMile's system; there is no API; the only route would be the auditor agent entering status/POD per shipment by proxy, which (a) depends on the audit account exposing such a screen, (b) makes iMile see the auditor, not the driver, as the deliverer, and (c) undermines G3 (who wrote what) and the attribution model the package builds on (`imile.driver_ids`, 3.12 — drivers deliver in the iMile app under their own iMile ID).
**Yes as a parallel layer, which is the current design:** the driver delivers in the iMile app; our agent reads the outcome; our driver app handles what iMile never sees — shift start and attendance, cage handover, custody and cash, ranking and commission, returns, grievance. Management stays on one screen; the driver uses two apps for different purposes, never duplicated work.
One external check owed (DEL_MGR): can the audit account record delivery/POD per shipment at all. If yes, the option exists but stays not recommended for the contractual reason above.

## 7. Clarification D-149 — warehouse field work on our PDA, exported to iMile in batches per user

Design: our PDA for all in-station work; each warehouse employee linked to their own iMile portal user (`imile.user_accounts`, role `warehouse`); an agent session per user pushes that user's operations to the portal in batches (`imile.export_batches`).
**Can agents enter operations directly and correctly? Yes, under conditions that are checked, not assumed:** bulk upload or per-shipment form must exist per scan type; one session per user; correctness by re-read reconciliation within 10 minutes plus the nightly inventory; idempotency key `tracking_no + scan_type + date + user`, failed batches replayed whole; batch delay 5–10 minutes accepted for sorting/inventory (receive-scan timing to confirm); UI-break protection as doc 07 §8.
Failure modes to verify first: operation only available from the iMile PDA app; iMile audit treating portal entries differently from PDA scans; rate limits; OTP per login (mail channel, D-148).
**External check owed:** one day, DEL_MGR + SYSADMIN, operations-manager account — for each scan type: bulk / single form / unavailable. Result gates the 3.14 brief.
