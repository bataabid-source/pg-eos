## The conflict

0.17's doc-38 acceptance criterion: *"Every role logs in and sees only its scope; SoD-violating
role assignment rejected; structure editable without deploy."* This requires, at minimum: real
login endpoints (OTP flow), session issuance/enforcement, RBAC/SoD evaluation wired into an API,
and an admin UI ("structure editor") a human can actually use.

Two rules collide with that:

1. **CLAUDE.md · BUILD METHOD:** *"GOLDEN SLICE = WBS 2.9 'Receive inbound order.' Built once with
   full human review. Every later slice replicates its file structure exactly. No file without a
   counterpart in the golden slice."* `.golden-slice-accepted` does not exist yet
   (`scripts/new-slice.sh` is a documented no-op until it does). A hand-built
   `modules/identity/{domain,application,infrastructure,api}` tree for 0.17 would be exactly the
   kind of hand-made file tree `CLAUDE.md · SPEED AND QUALITY` calls "a review FAIL."
2. **Circular dependency in doc 38's own Lane column:** WBS **0.19** ("Admin app shell:
   navigation, Decision Inbox, empty-state component, design system") depends on **0.17**. There is
   no admin app shell to put a "structure editor" screen into yet, and building one ad hoc for 0.17
   would duplicate 0.19's own job.

Every prior Phase-0 slice this session (0.9 through 0.16) sidestepped this exact tension by
building the underlying MECHANISM only — `withContext` (0.11), the outbox relay (0.12), the
document renderer (0.15), the column classifier (0.16) — and explicitly deferring the real
callers/UI/wiring to a later task once the golden slice and consuming modules exist. 0.17 is the
first task where the acceptance criterion itself is worded in a way that seems to assume the UI
and the golden-slice pattern already exist.
