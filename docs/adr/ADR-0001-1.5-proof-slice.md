## Context (السياق)

- **Dependency chain.** doc 38 row 2.9 (golden slice) depends on `2.4, 2.6, 2.8, 0.15`; row 2.6 (`wms.skus` with client ownership) depends on `1.5`; row 1.5 is "M02 `sales`: accounts, contacts, leads, opportunities, activities", acceptance "One account per client across entities; duplicate detection fires".
- **Why the dependency is real.** `wms.skus.client_id uuid not null references sales.accounts(id)` (01-Data-Model.sql l.640). A SKU cannot exist without a client account.
- **The rule it collides with.** CLAUDE.md BUILD METHOD: "Every later slice replicates its file structure exactly. No file without a counterpart in the golden slice." CLAUDE.md SPEED AND QUALITY: "Hand-made file trees are a review FAIL." A full 1.5 slice before 2.9 would hand-make a tree that 2.9 later defines; waiting would block 2.9 behind 1.5.
- **The schema already carries 1.5's data model.** `sales.accounts` (01 l.410–434): `code text not null unique`; no `entity_id` column, i.e. one row per client for the whole group (doc 40 §A2 l.46: "One `sales.accounts` row per client across all entities"); partial unique index on `cr_number` (01 l.435); RLS enabled (01 l.1441) with `client_portal_scope` for select (01 l.1476). Duplicate detection is the view `sales.possible_duplicates` (13B l.2129–2135, 13B-19). `sales.contacts`, `leads`, `opportunities`, `activities` are in 01 (l.438–497). `sales.accounts` is already exercised by the 0.18 isolation suite (`tests/isolation/tests/client-isolation.test.ts` l.202, l.302). No new table or column is needed.
- **The schema carries no sales seed.** No `insert into sales.` exists in 01 · 13 · 13B · 019. Unlike 2.1 (whose data is generated by `019-Warehouse-WH1-Setup.sql`), 1.5's seed has no schema source. Real client data enters only through the human data gate 1.10 (doc 38: "all current clients with CR and contact", owner CFO).
- **Precedents.** 2.1 was built as a proof-only slice ("the schema file … already delivers the data; the slice is the permanent, re-runnable proof" — CHANGELOG 2.1). 0.17 was delivered as mechanisms only under the Phase-0 GM ruling of 2026-09-22 and is `DONE (mechanisms)`, excluded from the completion ratio (MASTER_BACKLOG 0.17).

## Decision (القرار)

1.5 is built as a **limited proof slice in the 2.1 pattern — data model + seed only, no UI, no workflow, no public API** — to unblock 2.6 → 2.9. The **full** 1.5 slice is replicated later from the golden slice 2.9. 1.5's status becomes **`DONE (proof)`** and it is **excluded from the completion ratio**.

Application of the decision (no widening of it):

- **Data model:** the M02 tables as they already stand in 01 · 13B. No migration, no schema change.
- **Seed:** the accounts (and their contacts) that 2.6 needs. It contains no real client name, CR number, credit limit or other business value — none exists in the schema and none may be invented (CLAUDE.md AGENT CONSTRAINTS). Rows are labelled test fixtures created and removed by the proof suite (0.18 precedent). A persistent seed file would be an object outside 01/13/13B/019 and requires an SCR under G-01 first.
- **Proof:** a Gherkin scenario and a proof suite asserting doc 38's 1.5 acceptance **where it is provable at the schema level**: one row per client (no `entity_id`; `code` unique; `cr_number` partial unique index), RLS on `sales.accounts`, and `sales.possible_duplicates` returning a near-duplicate pair.
- **Not in scope:** screens, lead/opportunity state machines, the duplicate-merge service (INV-C2-3 "merge, never delete"), API endpoints, events.

## Alternatives rejected (البدائل المرفوضة)

| Alternative | Why rejected |
|---|---|
| A. Build the full 1.5 slice before 2.9 | Hand-made file tree before the golden slice exists (CLAUDE.md SPEED AND QUALITY: review FAIL); the tree would be rebuilt when 2.9 becomes the template. |
| B. Re-point 2.6's dependency away from 1.5 in doc 38 | Changes the governing task sequence (doc 38 header: "GOVERNING (the only task sequence, rank 5)") for a scheduling convenience; `wms.skus.client_id` is `not null` and references `sales.accounts`. |
| C. Build 2.6 / 2.9 on an ad-hoc client row without 1.5 | Bypasses the doc-38 edge 2.6 → 1.5 and leaves the upstream table the golden slice depends on unproven (one account per client, duplicate detection). |
| D. Wait for Phase 1 to complete | 2.9 — the template for every later slice — would wait on the 11 Phase-1 tasks, including the two human data gates 1.3 and 1.10 (owner CFO). |

## Consequences (الأثر)

- **Positive:** 2.6 becomes buildable after 1.5 (proof). 2.9 then still needs 2.4 (via 2.2 field survey — human, owner WH_MGR, WAITING_GM — and 2.3), 2.8, and the Phase-0 gate to close (PROJECT_STATE: "2.9 does not start before it closes"). 0.15 is DONE.
- **Negative / risks:** two partial-DONE states exist (0.17 mechanisms, 1.5 proof); both are excluded from the ratio and tracked in MASTER_BACKLOG with the task that completes them (0.19 for 0.17; the post-2.9 replication for 1.5). A reviewer must not accept a proof slice as meeting doc 38's acceptance criterion.
- **Known discrepancy the proof must surface, not absorb:** doc 40 INV-C2-3 says name similarity "≥ 0.85"; the view uses `> 0.85` (13B l.2135). A pair at exactly 0.85 is a duplicate under doc 40 and not under the view. The proof tests the doc-40 boundary; if it fails, file an SCR under G-01 — never weaken the test.
  - **Resolution (2026-09-23, GM directive phase D):** the view is corrected to `>= 0.85` by migration `0006_M_possible-duplicates-ge.sql` / 13B v4.4 §13B-19. Measured on PostgreSQL 16.15: `similarity()` returns `real` and is compared with `(0.85)::double precision`; float4(0.85) = 0.8500000238 > 0.85, so an exact-0.85 pair was already reported by the old `>` — the statement above ("not under the view") did not hold on PG 16. The proof is therefore the normalized view text (3a, RED before 0006) plus a non-regression boundary test (3b). Duplicate detection on Arabic `name_ar` additionally requires `lc_ctype = C.UTF-8` (SCR-TRGM-01, option A approved by the GM 2026-09-23): under `C` pg_trgm produces no Arabic trigrams and similarity is 0.
- **Scope:** this ADR covers 1.5 only. It does not decide how 2.6 or 2.8 (also prerequisites of 2.9) are built.
- **Why this is an ADR:** it alters a CLAUDE.md BUILD METHOD rule ("No file without a counterpart in the golden slice") for one named task. The system's runtime architecture is unchanged.
- **Guards:** no SCR is needed for the objects the proof uses (all exist in 01/13B). G6 covers the `sales` schema and returns 0 (PROJECT_STATE); G7 already returns 0.
