# سيناريو 1 — عميل 3PL متكامل (SEG-A)

## بيانات القبول التنفيذية (40 Part E · `Feature: S1 Full 3PL client (Segment A, PST + PDL)`)

| البند | القيمة الحرفية في الاختبار |
|---|---|
| كود العميل | `GULF` |
| كود الصنف | `GULF-0137` |
| رقم الدفعة | `B2409-7` |
| الحد الأدنى للصلاحية عند الاستلام | **180 يوماً** (العقد) — دفعة بصلاحية **120 يوماً** تدخل منطقة `QRT` |
| بند القرار المتولّد | `quarantine_decision` — نافذة تواصل العميل **48 ساعة** |
| التحقق السلبي | **لا `stock_movement` إلى موقع تخزين** لتلك الدفعة |
| التخصيص | دفعتان بصلاحية **90** و**200** يوماً · أمر صرف **12 وحدة** ⇒ FEFO يأخذ الاثنتي عشرة من دفعة الـ**90** |
| أحداث الفوترة بعد التدقيق | `OF-01 ×1` · `OF-02 ×1` · `OF-06 ×1` · `OF-07 ×1` — بحالة `pending` |
| النتيجة | مهمة التوصيل تُنشأ في **PDL** |

## الملف
شركة توزيع مستحضرات تجميل · 320 منصة تخزين · 2,400 طلب تجزئة شهرياً · توصيل B2C داخل الكويت · أصناف بصلاحية.

| البند | القيمة |
|---|---|
| الكيانات | PST (تخزين وتجهيز) · PDL (توصيل) |
| الشريحة | SEG-A — إيراد شهري ~6,800 د.ك |
| العقود | عقدان: PST و PDL · دورة فوترة شهرية · سداد 30 يوماً |
| الحد الائتماني | 15,000 د.ك على مستوى المجموعة |

## الخدمات المتعاقد عليها

| الفئة | الخدمات |
|---|---|
| تخزين | ST-01 (مبرَّد ST-05 لـ12%) · ST-11 حد أدنى 2,000 د.ك |
| مناولة | HD-03 · HD-04 · HD-07 · HD-08 |
| تجهيز | OF-01 · OF-02 · OF-03 · OF-06 · OF-07 |
| توصيل | DL-01 · DL-07 · DL-10 · **DL-11 و DL-12 منصوص عليهما** |
| قيمة مضافة | VA-06 (فرز مرتجعات) |

## الدورة داخل النظام

```
① العميل ينشئ ASN من نافذته
     → فحص: عقد ساري ✓ · بلا حجز ✓
     → wms.inbound_orders (draft → approved)

② وصول الشاحنة → PDA
     → مسح الصنف · دفعة · صلاحية
     → صلاحية متبقية < 180 يوماً؟ → حجر + قرار العميل
     → GRN يُولَّد ويُرسل تلقائياً
     → أحداث فوترة: HD-03 ×1 · HD-04 ×48 · HD-07 ×48 · HD-08 ×48

③ التخزين
     → النظام يقترح مواقع بشروط الصنف (مبرَّد → منطقة C)
     → لقطة إشغال يومية 00:30 → ST-01 و ST-05 يومياً

④ طلب تجزئة من نافذة العميل
     → فحص الشروط العشرة
     → تخصيص FEFO (صلاحية أقرب أولاً)
     → قائمة التقاط بالتسلسل الأمثل
     → التقاط → تدقيق → تغليف → تحميل
     → أحداث: OF-01 ×1 · OF-02 ×4 · OF-06 ×1 · OF-07 ×1

⑤ مهمة توصيل تلقائية في PDL
     → تسليم ناجح → POD (GPS + توقيع) → DL-01 + DL-10 (COD)
     → فشل → DL-11 (منصوص) → محاولة 2 → فشل → DL-12 + مرتجع

⑥ المرتجع يعود للمستودع
     → HD-10 (استلام مرتجع) · VA-06 (فرز)
     → صالح → المخزون · تالف → منطقة التالف

⑦ إقفال الشهر
     → PST تفوتر: تخزين + مناولة + تجهيز + VAS
     → PDL تفوتر: توصيل + COD + محاولات فاشلة + إرجاعات
     → فاتورتان منفصلتان (قانوني) + كشف موحّد (إداري)
     → ورقة تفصيل بكل حدث ومرجعه وسعره
```

## نقاط الحذر

| النقطة | المعالجة |
|---|---|
| الحد الأدنى الشهري | إن قلّ الاستهلاك عن 2,000 → يُفوتر ST-11 والفرق فقط |
| تجاوز المساحة المتعاقدة | ST-12 على المنصات الزائدة آلياً من لقطة الإشغال |
| مطابقة COD | المحصَّل ≠ المستحق → فرق مفتوح يمنع إقفال يوم السائق |
| السحب من السوق | دفعة تالفة → النظام يجيب فوراً: لأي عملاء صُرفت وبأي شحنات |

# سيناريو 2 — عميل 2PL تخزين فقط (SEG-C)

## بيانات القبول التنفيذية (40 Part E · `Feature: S2 2PL storage-only client`)

| البند | القيمة الحرفية في الاختبار |
|---|---|
| كود العميل | `PARTS` |
| خدمات العقد **حصراً** | `ST-01` · `ST-11` · `HD-03` · `HD-04` · `HD-08` · `OF-10` |
| الواقعة المختبَرة | تنفيذ **`VA-08`** (تغليف انكماشي) للعميل — وهي **خارج العقد** |
| النتيجة المطلوبة | حدث فوترة `VA-08` بحالة **`pending` وبلا سعر** — لا يُسقط ولا يُفوتر |
| التحقق | يظهر في **تقرير الإيراد الضائع** |

## الملف
مستورد قطع غيار · 60 منصة · يسحب بضاعته بمركباته · لا تجهيز ولا توصيل.

| البند | القيمة |
|---|---|
| الكيان | PST فقط |
| الشريحة | SEG-C — إيراد ~900 د.ك |
| الخدمات | ST-01 · ST-11 (حد أدنى 600) · HD-03 · HD-04 · HD-08 · OF-10 (صرف منصة كاملة) |

## الفرق الجوهري عن السيناريو 1

| البند | المعالجة |
|---|---|
| الصرف | `order_type = 'standard'` **بلا مهمة توصيل** — ينتهي عند «محمَّل» |
| الاستلام من العميل | العميل يمسح إذن الصرف عند البوابة · توقيع مندوبه إثبات التسليم |
| التجهيز | لا OF-01..OF-07 — فقط OF-10 بالمنصة الكاملة |
| نافذة العميل | مخزون وحركات وأوامر · **بلا تتبّع شحنات** |

**نقطة حذر:** عميل 2PL كثيراً ما يطلب «خدمة صغيرة» خارج العقد (تغليف · فرز · انتظار مركبة). النظام يسجّلها كحدث بلا سعر → تقرير الاستثناءات → إما تُسعَّر أو تُعتمد مجاناً بقرار مسجَّل. **لا تضيع صامتة.**

# سيناريو 3 — توصيل استهلاكي B2C (SEG-B)

## بيانات القبول التنفيذية (40 Part E · `Feature: S3 B2C delivery with SLA`)

| البند | القيمة الحرفية في الاختبار |
|---|---|
| كود العميل | `SHOP` |
| العلم العقدي | **`bills_failed_attempt = true`** |
| الشرط المسبق | مهمة عليها **محاولتا اتصال مسجَّلتان** |
| سبب الفشل | `no_answer.no_response` (من القائمة المغلقة) |
| النتيجة | يُنشأ حدث فوترة **`DL-11`** · و**`counts_against_driver = false`** |
| اختبار العنوان الناقص | مهمة بمنطقة `Salmiya` **بلا قطعة ولا شارع** ⇒ الواجهة البرمجية تعيد **`422`** تُعدّد الحقول الناقصة |

## الملف
متجر إلكتروني · 1,800 شحنة شهرياً · COD 70% · تسليم خلال 48 ساعة · بضاعته في مستودعه.

| البند | القيمة |
|---|---|
| الكيان | POR |
| الخدمات | DL-01 · DL-07 · DL-10 · DL-11 ✅ · DL-12 ✅ · DL-14 ✅ · CC-08 (تأكيد الطلبات) |
| SLA | نسبة التسليم من المحاولة الأولى ≥ 85% · غرامة 3% من الفاتورة الشهرية عند الإخلال |

## الدورة

```
① استيراد الشحنات: API أو ملف أو نافذة العميل → tms.delivery_tasks
② PCC يؤكد الطلبات قبل التوزيع (CC-08) → إلغاء المؤكَّد رفضه قبل الخروج
③ خطة التوزيع مساءً: مناطق · أحمال · تدوير
④ صباحاً: تسليم بالمسح → الحالة «خرجت»
⑤ تسليم → POD إلزامي (GPS + توقيع/صورة + اسم المستلم)
⑥ فشل → سبب من قائمة مغلقة → DL-11 → محاولة 2 → DL-12 + مرتجع
⑦ ليلاً: مطابقة COD · مصالحة · توليد الأحداث
⑧ شهرياً: قياس SLA → إن < 85% تُحتسب الغرامة وتُخصم في الفاتورة
```

## نقاط الحذر

| النقطة | المعالجة |
|---|---|
| **العنوان الناقص** | أكبر سبب فشل. النظام يرفض المهمة بلا: منطقة · قطعة · شارع · هاتف |
| تكرار الشحنة | فهرس فريد على (المصدر + مرجع المصدر) يمنع الإدخال المزدوج |
| COD غير محصَّل | فرق مفتوح · لا يُقفل يوم السائق · تقرير يومي للمالية |
| غرامة SLA | تُحسب آلياً من البيانات وتظهر كسطر خصم في الفاتورة — لا نقاش تقديري |

## الدورة

```
① مكالمة واردة → طابور العميل → توجيه لوكيل مؤهَّل بمهارة اللغة
② الوكيل يرى شاشة العميل المخصّصة (سكربت · نظام مواعيد · أسئلة شائعة)

④ إقفال بحقل حل إلزامي → استبيان رضا
⑤ شهرياً: CC-03 ×4 ثابت + مكالمات التجاوز + CC-11 + CC-12 + CC-13
⑥ قياس SLA → غرامة أو حافز حسب العقد
```

## نقاط الحذر

| النقطة | المعالجة |
|---|---|
| **عزل بيانات العميل** | وكيل PCC لا يرى تذاكر عميل آخر — RLS على `queue_id` |
| موسمية الحجم | باقة ثابتة + تجاوز تحمي الطرفين |
| تسريب التسجيلات | تصنيف `secret` على روابط التسجيل · وصول بصلاحية صريحة فقط |
| وكيل يخدم عدة عملاء | مقعده يُوزَّع نسبياً في تكلفة العمالة — وإلا اختلّت الربحية |

# سيناريو 6 — عميل متعدد الكيانات (SEG-A)

## بيانات القبول التنفيذية (40 Part E · `Feature: S6 Multi-entity client`)

| البند | القيمة الحرفية في الاختبار |
|---|---|
| كود العميل | `RETAIL` — بعقود مع **PST و PDL و PCC** |
| الحد الائتماني | **15,000** على مستوى المجموعة |
| المحفّز | فاتورة **PST** متأخرة ترفع الانكشاف فوق الحد |
| متى | عند تشغيل **الوظيفة الليلية** |
| النتيجة | `credit_hold = true` · **أمر صرف PST يُرفض بسبب `credit hold`** · **ومهمة توصيل PDL تُرفض بالسبب نفسه** · **وطابور PCC جديد للعميل يُرفض** |

## الملف
سلسلة تجزئة · تخزين في PST · توصيل في PDL · خدمة عملاء في PCC.

## المعالجة — نقطة الاختبار الأصعب في النظام

```
سجل CRM واحد: sales.accounts (حساب واحد)
       │
       ├─► عقد PST  ──► فواتير PST  ──┐
       ├─► عقد PDL  ──► فواتير PDL  ──┼──► كشف حساب موحّد (إداري)
       └─► عقد PCC  ──► فواتير PCC  ──┘
                                        │
                           حد ائتماني واحد على مستوى المجموعة
```

| البند | القاعدة |
|---|---|
| العميل | **سجل واحد** — لا تكرار |
| العقود | ثلاثة · لكل كيان التزامه القانوني |
| الفواتير | **ثلاث فواتير من ثلاثة كيانات — قانوني إلزامي** |
| كشف الحساب | موحّد على المجموعة + مفصّل لكل كيان |
| **الحد الائتماني** | **واحد على المجموعة** — يُستهلك من الثلاثة |
| **الحجز الائتماني** | **يمنع الصرف في الكيانات الثلاثة معاً** — لا التفاف |
| الشريحة | تُحسب على إجمالي التعامل مع المجموعة |

## اختبار القبول الحاسم

> العميل تجاوز حده الائتماني بفاتورة PST متأخرة.
> **النتيجة المطلوبة:** يُرفض أمر صرف من PST **وأمر توصيل من PDL** — بنفس رسالة السبب.
> إن نجح الأمر في PDL، فالتصميم فاشل.

# سيناريو 7 — عميل تجريبي / موسمي (SEG-F / SEG-E)

## بيانات القبول التنفيذية (40 Part E · `Feature: S7 Trial client`)

| التسعير | العروض تستخدم **أسعار القائمة القياسية بلا أي خصم** |
| الائتمان | **`credit_limit = 0`** |
| التنبيه | يُطلق **قبل انتهاء العقد بأربعة عشر يوماً** |

> **فجوة تغطية معلومة (ADM-46):** هذا السيناريو يجمع **SEG-F التجريبي** و**SEG-E الموسمي** في ملف واحد، بينما 40 S7 يختبر **SEG-F وحده** (`Given client "TRIAL" in segment F`). فقاعدة الموسمي أدناه — «الحد الأدنى يُطبَّق في أشهر النشاط فقط» — **لا يغطيها أي اختبار قبول**. المعالجة المطلوبة: إضافة `Scenario` ثانٍ إلى 40 S7 يختبر **SEG-E** بـ`min_monthly_charge` مقيَّداً بأشهر معلَنة في العقد. مسجَّل في `_changelog/CHANGELOG-ADM.md` تحت «يحتاج تحكيم» لأن تعديل 40 خارج نطاق هذا الوكيل.

| البند | القاعدة |
|---|---|
| العقد | مدة محددة · `auto_renew = false` |
| الأسعار | **أسعار القائمة القياسية — بلا خصم شريحة** |
| الحد الائتماني | صفر — **دفع مقدم أو عند التسليم** |
| المراجعة | تنبيه قبل الانتهاء بـ 14 يوماً → تحويل إلى شريحة دائمة أو إنهاء |
| الموسمي (SEG-E) | الحد الأدنى يُطبَّق في أشهر النشاط فقط — **بند عقدي صريح** · **بلا اختبار قبول حتى اليوم** |

**نقطة حذر:** العميل التجريبي هو أكثر من يُقدَّم له خدمات مجانية غير موثّقة. النظام يسجّل كل حدث حتى غير المسعَّر، ويظهر في تقرير الاستثناءات — **فتُعرف تكلفة التجربة الحقيقية قبل قرار التحويل.**
