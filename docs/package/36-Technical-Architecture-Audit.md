# 1. النمط المعماري — قرار مُلزم

## 1-1 المونوليث المعياري (Modular Monolith)

**لا خدمات مصغّرة.** لخمسة عشر إلى ثمانين مستخدماً، الخدمات المصغّرة عبء تشغيلي بلا عائد — **والوكلاء الذكية تبني الأنظمة الموزّعة بشكل رديء**.

```
تطبيق واحد · قاعدة واحدة · نشر واحد
      │
      ├── مخطط لكل موديول (schema)          ← عزل البيانات
      ├── حزمة لكل موديول (package)         ← عزل الكود
      ├── حدود مفروضة بالأدوات              ← لا استيراد عبر الحدود
      └── تواصل عبر الأحداث والعقود فقط     ← لا استدعاء مباشر
```

| القاعدة | الفرض |
|---|---|
| موديول لا يستورد من موديول آخر | `eslint-plugin-boundaries` — **يفشل البناء** |
| موديول لا يقرأ جدول موديول آخر | RLS + مستخدم قاعدة لكل مخطط |
| التواصل بين الموديولات | حدث مجال **أو** عقد معلن في `contracts/` |
| الفصل لاحقاً إلى خدمة | ممكن — لأن الحدود مفروضة من اليوم الأول |

## 1-2 المعمارية السداسية داخل كل موديول

**كل موديول بنفس البنية حرفياً.** هذا ما يجعل الوكيل يبني الموديول العاشر بجودة الأول.

```
modules/wms/
├── domain/              ← القلب: كيانات · قيم · قواعد ثابتة · أحداث
│   ├── entities/          Location · Sku · StockMovement
│   ├── value-objects/     Quantity · LocationCode · Weight
│   ├── invariants/        noNegativeStock · maxWeightPerLocation
│   ├── events/            InboundReceived · OutboundChecked
│   └── state-machines/    outboundOrder.machine.ts   ← XState
├── application/         ← حالات الاستخدام: أمر واحد لكل ملف
│   ├── commands/          ReceiveInbound · AllocateOutbound
│   ├── queries/           GetStockBalance · TraceShipment
│   └── ports/             StockRepository · LabelPrinter   ← واجهات
├── infrastructure/      ← التنفيذ: قاعدة · ملفات · تكاملات
│   ├── repositories/      DrizzleStockRepository
│   └── adapters/          PdfLabelPrinter
├── api/                 ← الواجهة: مسارات · تحقق · تحويل
│   ├── routes/
│   └── schemas/           Zod ← مصدر OpenAPI
└── tests/
    ├── domain/            وحدات — بلا قاعدة
    ├── application/       تكامل — قاعدة اختبار
    └── scenarios/         القبول — من وثيقة 05 و 12
```

**القاعدة الذهبية:** `domain/` **لا يستورد شيئاً** من الطبقات الأخرى ولا من أي مكتبة خارجية. قواعد الأعمال نقية — تُختبر بلا قاعدة وبلا شبكة في أجزاء من الثانية.

## 1-3 الشرائح الرأسية

**الوكيل لا يبني «طبقة» — يبني «شريحة»:** من المخطط إلى الشاشة لحالة استخدام واحدة.

```
شريحة «استلام أمر إدخال»:
  هجرة SQL → كيان + قاعدة ثابتة → أمر → مستودع → مسار API → مخطط Zod
  → شاشة PDA → اختبار وحدة + تكامل + قبول
```

الشريحة تُسلَّم كاملة وتعمل، أو لا تُسلَّم. **لا «انتهيت من الخلفية، الواجهة لاحقاً».**

**المعمارية لا تتغيّر بين المستويات** — نفس `docker-compose.yml` يعمل على أي هدف. ما يلي هو تحليل المستوى ٢:

| المعيار | Google Cloud | AWS | Azure |
|---|---|---|---|
| أقرب منطقة للكويت | الدوحة ~٣٠٠ كم · الدمام | البحرين ~٤٥٠ كم · الإمارات | الدوحة · الإمارات |
| **منطقة كويتية معلَنة** | ✅ **معلَنة** — يُتحقق من إتاحتها عند الإعداد | ❌ | ❌ |
| الحاويات لحجمنا | **Cloud Run** — تصغير للصفر · أبسط وأرخص | ECS/Fargate — أثقل | Container Apps |
| Postgres مُدار | Cloud SQL 16 | RDS | Flexible Server |
| **التكامل مع Google Workspace** | ✅ **هوية موحّدة · فوترة موحّدة · إدارة موحّدة** | ❌ | ❌ |
| Terraform | ناضج | الأنضج | ناضج |
| التكلفة عند ١٥–٨٠ مستخدماً | **الأدنى** | الأعلى | متوسط |

**لماذا Google Cloud تحديداً:**
1. **أنتم على Google Workspace** (Gmail · Drive · Calendar) — الدخول الموحّد والفوترة والإدارة في مكان واحد. لفريق تقني صغير هذا فارق تشغيلي حقيقي.
2. **Cloud Run** أبسط منصة حاويات وأرخصها — تتصغّر للصفر خارج الدوام. NestJS في حاوية + Cloud SQL = أنحف مكدّس مؤسسي.
3. **منطقة كويتية معلَنة** — الانتقال إليها **تغيير متغيّر في Terraform** لا تغيير مزوّد.
4. الدوحة داخل مجلس التعاون — تُبقي البيانات في المنطقة.

**⚠️ ملاحظتان:**
- منطقة **الدمام** لها قيود شراء لعناوين الفوترة السعودية — **الدوحة** هي الخيار الآمن للفوترة الكويتية.
- إن أوجب القانون الكويتي بقاء البيانات **داخل الكويت** (الخطر R5)، فالخيار: منطقة الكويت عند إتاحتها، أو قاعدة البيانات وحدها لدى مزوّد محلي مع بقاء الحوسبة في الدوحة.

**البديل الثاني إن تعذّر:** AWS البحرين — الأنضج، وأقرب منطقة **متاحة** للكويت اليوم.

**ما يُستبعد:** Supabase — لا منطقة خليجية، وتحكم مؤسسي أقل. المزوّدون المحليون — لا مكافئ لـCloud Run ولا Terraform ناضج.

# 3. الأنماط المؤسسية الإلزامية — ستة كانت غائبة

## 3-1 الصندوق الصادر للأحداث (Transactional Outbox)

**الثغرة السابقة:** `platform.domain_events` مصمَّم كجدول — لكن بلا ضمان أن الحدث يُكتب **في نفس معاملة** تغيير الحالة. النتيجة: حدث ضائع أو مكرّر. **القرار النافذ (v4): `platform.outbox` هو الجدول الحاكم للأحداث، و`platform.domain_events` محذوف في 13B.** كل وثيقة تذكر `domain_events` تعني `outbox`.

```
معاملة واحدة:
  ① تحديث الحالة       (wms.outbound_orders.status = 'checked')
  ② إدراج الحدث        (platform.outbox)
  COMMIT
       ▼
ناقل (Relay) كل ثانية: يقرأ outbox غير المعالج → ينشر → يعلّم
       ▼
مشتركون: فوترة · وثائق · تنبيهات · تدقيق
```

**التعريف النافذ في `13B` — لا يُكرَّر في أي هجرة ولا في أي شريحة:**

```sql
-- database/13B-Schema-Reference-Consolidation.sql
create table platform.outbox (
  id bigserial primary key,
  aggregate_type text not null, aggregate_id uuid not null,
  event_type text not null, payload jsonb not null,
  correlation_id uuid not null, causation_id uuid,
  created_at timestamptz not null default now(),
  published_at timestamptz,
  attempts int not null default 0, last_error text,
  actor_id uuid                       -- v4: الفاعل المسبِّب (31 §5)
);
create index on platform.outbox (published_at) where published_at is null;
create index on platform.outbox (correlation_id);   -- v4: هدف التتبّع ≤ 2 ث
drop table if exists platform.domain_events;        -- v4: الجدول المتقاعد
```

**مُنفَّذ في 13B (SCR-1):** العمود `entity_id uuid` على `platform.outbox` مع سياسة `entity_scope`؛ يُترك فارغاً فقط للحدث المنصّي العابر للكيانات (`platform.*` / `identity.*`) بقيد `outbox_business_needs_entity`، ويراه الداخلي فقط. لا تلتفّ أي شريحة على ذلك بكتابة الكيان داخل `payload`.

**الضمان:** الحدث يُكتب أو لا يُكتب **مع** الحالة — لا حالة ثالثة.

## 3-2 مفتاح التفرّد على كل أمر

```
POST /api/v1/wms/inbound/receive
Idempotency-Key: 7c9e6679-7425-40de-944b-e07fc1f90ae7
```

| القاعدة | |
|---|---|
| كل نقطة كتابة تتطلب المفتاح | **رفض ٤٠٠ بدونه** |
| المفتاح + الجسم المتطابق | يعيد النتيجة السابقة — لا تنفيذ ثانٍ |

## 3-3 التزامن التفاؤلي

```sql
alter table wms.outbound_orders add column version int not null default 1;
-- كل تحديث: WHERE id = $1 AND version = $2 → SET version = version + 1
-- صفر صفوف متأثرة = تعارض → 409
```

**كل كيان قابل للتعديل يحمل `version`.** مشرفان يعدّلان الأمر نفسه: الثاني يُرفض برسالة واضحة — لا يُمسح تعديل الأول بصمت.

## 3-4 طبقات التحقق الثلاث

| الطبقة | ما تمنعه | الأداة |
|---|---|---|
| **الحدود** (API) | شكل خاطئ · نوع خاطئ | Zod |
| **المجال** | قاعدة أعمال مخروقة | `invariants/` |
| **القاعدة** | آخر خط دفاع | `CHECK` · `UNIQUE` · `FK` |

**الثلاث معاً — لا واحدة.** الوكيل قد ينسى قاعدة في المجال؛ القاعدة تمسكها. قد يُخترق الـAPI؛ المجال يمسكها.

## 3-5 حقن سياق RLS — إلزامي في كل معاملة

```ts
// الطريقة الوحيدة المسموحة لفتح معاملة
await db.transaction(async (tx) => {
  await tx.execute(sql`SET LOCAL app.user_id = ${ctx.userId}`);
  await tx.execute(sql`SET LOCAL app.is_internal = ${ctx.isInternal}`);
  await tx.execute(sql`SET LOCAL app.client_id = ${ctx.clientId ?? ''}`);
  // ... العمل
});
```

**قاعدة lint:** أي استدعاء `db.` خارج `withContext()` **يفشل البناء**. هذا ما يجعل RLS حاجزاً لا أمنية.

## 3-6 أعلام الميزات ومفاتيح الإيقاف

```sql
create table platform.feature_flags (
  key text primary key,
  enabled boolean not null default false,
  rollout_pct int not null default 100,        -- إطلاق تدريجي
  enabled_for_roles text[],
  kill_switch boolean not null default false,  -- إيقاف طارئ يتجاوز كل شيء
  changed_by uuid, changed_at timestamptz
);
```

**كل ميزة جديدة خلف علم.** الإطلاق = تفعيل علم لا نشر. الرجوع = إطفاؤه في ثانية.

# 4. الطبقة التشغيلية المؤسسية

## 4-1 المراقبة (Observability)

| الركن | الأداة | المتطلب |
|---|---|---|
| **سجلات مهيكلة** | pino → JSON | كل سطر يحمل `correlation_id` · `user_id` · `module` |
| **تتبّع موزّع** | OpenTelemetry | طلب واحد من الواجهة إلى القاعدة إلى الطابور كشجرة واحدة |
| **مقاييس** | Prometheus + Grafana | p95 لكل مسار · أعماق الطوابير · فشل التكاملات · أخطاء ٥xx |
| **أخطاء** | Sentry أو مكافئ | كل استثناء مع سياقه · تجميع · تنبيه |
| **فحص الصحة** | `/health` · `/ready` | القاعدة · الطابور · التكاملات الحرجة |

**قاعدة:** لا يُنشر شيء لا يُرى. **لوحة Grafana واحدة لكل موديول** تُبنى مع الموديول لا بعده.

## 4-2 البنية التحتية ككود

| البند | القرار |
|---|---|
| الأداة | **Terraform** |
| ما يُعرَّف | القاعدة · التخزين · الشبكة · الأسرار · المراقبة · النطاقات |
| البيئات | `dev` · `staging` · `prod` **من نفس الكود بمتغيرات مختلفة** |
| التغيير | عبر مراجعة كود — **لا نقر في لوحة تحكم** |
| الاستنساخ | بيئة كاملة جديدة بأمر واحد |

**بدون هذا:** البيئات تتباعد بصمت، و«يعمل عندي» يصير القاعدة.

## 4-3 خط النشر

**سبع بوابات مسمّاة ①–⑦** — هذا العدد والتسمية هما المرجع في §7 وفي مهمة 38 §0.6.

```
دفع الكود
   ▼
① STATIC      lint + حدود الموديولات + أنواع صارمة        ← ثوانٍ
② UNIT        اختبارات الوحدة (domain) ≥ ٩٠٪              ← ثوانٍ
③ INTEGRATION اختبارات التكامل على قاعدة مؤقتة           ← دقائق
④ ACCEPTANCE  السيناريوهات العشرون S1–S20 (Playwright)     ← دقائق
⑤ GUARDS      الاختبارات الحارسة G1–G18 (الوثيقة 40 الجزء F · database/guards.sql)
⑥ SECURITY    تبعيات · أسرار مسرّبة · SBOM                ← دقيقة
⑦ BUILD       بناء الصور + الهجرات                          
   ▼
نشر تلقائي إلى staging
   ▼ اختبار دخاني + موافقة مالك النظام
نشر إلى prod — أزرق/أخضر · رجوع بأمر واحد
```

| البوابة | الاسم | شرط النجاح |
|---|---|---|
| ① | STATIC | صفر خطأ lint · صفر خرق حدود · صفر `any` |
| ② | UNIT | تغطية `domain/` ≥ ٩٠٪ |
| ③ | INTEGRATION | كل أمر واستعلام أخضر على قاعدة مؤقتة |
| ④ | ACCEPTANCE | **20/20** من السيناريوهات S1–S20 |
| ⑤ | GUARDS | **G1–G18** كل واحد يحقّق شرطه المنصوص (ليس «صفر صفوف» لجميعها: G13 = 100 فريد · G15 = 20/20 · G16 ≥ ٧٥٪ · G17 ≤ ٢ ث · G18 تقرير لا يحجب) |
| ⑥ | SECURITY | صفر ثغرة حرجة/عالية · صفر سر مسرَّب · SBOM مولَّد |
| ⑦ | BUILD | الصور تُبنى لـ`linux/arm64` والهجرات تُطبَّق وتُعكَس |

**أي بوابة حمراء توقف الخط. لا استثناء ولا «سننشر ونصلح».**

## 4-4 فصل القراءة عن الكتابة

| الاستخدام | المصدر |
|---|---|
| العمليات (OLTP) | القاعدة الأساسية |
| **التقارير والتحليلات** | **نسخة قراءة (Read Replica) — هدف Tier 1/2.** في Tier 0 (المراحل 0–3) لا توجد نسخة قراءة: التقارير تُشغَّل على القاعدة الأساسية خارج ساعات الذروة بـ`statement_timeout` صريح |

| التحليل التاريخي | مخطط `analytics` منفصل · لاحقاً مستودع بيانات |

**بدون هذا:** تقرير الربحية الشهري يُبطئ استلام المستودع.

# 5. منهجية البناء بالذكاء الاصطناعي

## 5-1 المبدأ: المواصفة تقود، لا الوكيل

**الوكيل الذكي يبني بامتياز ما هو محدَّد، ويخترع بكارثية ما هو غامض.**

```
لكل شريحة، بهذا الترتيب — ولا يُقفز خطوة:

① السيناريو       ← من وثيقة 05/12 · بصيغة Given/When/Then
② العقد           ← مخطط Zod + OpenAPI · يُراجَع قبل أي كود
③ الهجرة          ← SQL مع RLS وقيود · تُراجَع
④ الاختبارات      ← تُكتب أولاً من السيناريو · حمراء
⑤ المجال          ← كيانات وقواعد ثابتة حتى تخضرّ اختبارات الوحدة
⑥ التطبيق         ← الأمر والمستودع حتى تخضرّ اختبارات التكامل
⑦ الواجهة         ← من العقد · حتى يخضرّ سيناريو القبول
⑧ المراجعة        ← بشرية · على القائمة في §5-4
```

**الاختبار قبل الكود ليس ترفاً هنا — هو الآلية الوحيدة التي تجعل الوكيل يبني ما طُلب لا ما ظنّ.**

## 5-2 الشريحة الذهبية

**أول شريحة تُبنى بعناية بشرية كاملة، وتصير القالب.**

الشريحة الذهبية هي **المهمة 2.9 في الوثيقة 38 (WBS 2.9)**: **«استلام أمر إدخال — Receive inbound order»** — لأنها تمرّ بكل الطبقات: PDA · آلة حالة · دفتر مخزون · حدث · وثيقة GRN · أحداث فوترة.

| البند | القيمة (منقولة من 38 المهمة 2.9) |
|---|---|
| رقم المهمة | **2.9** |
| الاعتماديات | 2.4 · 2.6 · 2.8 · 0.15 |
| المالك | WH_MGR + مراجعة المدير العام |
| **معيار القبول** | **مراجعة بشرية كاملة؛ الشريحة تصير القالب** (`Full human review; becomes the template`) |
| النموذج | يُسمح بـ`opus` للجلسة كاملة (بناءً ومراجعةً) — الاستثناء الوحيد |

بعدها، كل شريحة تُبنى بأمر واحد للوكيل:

```
ابنِ شريحة «تخصيص أمر صرف» باتباع بنية شريحة «استلام أمر إدخال» حرفياً:
- نفس تقسيم المجلدات
- نفس نمط الأمر والمستودع والمسار
- نفس نمط الاختبارات الثلاثة
- السيناريو: [يُلصق]
- العقد: [يُلصق]
لا تُنشئ ملفاً في مكان لا يقابله ملف في الشريحة الذهبية.
```

## 5-3 حدود الوكيل — تُلصق في كل جلسة

| ممنوع | البديل |
|---|---|
| إنشاء جدول أو عمود أو قاعدة عمل خارج `01 / 13 / 13B / 019` | طلب تغيير مخطط (SCR) بسطر واحد تحت G-01 |
| استيراد عبر حدود موديول | حدث أو عقد |
| `db.` خارج `withContext()` | — يفشل lint أصلاً |
| `any` · `@ts-ignore` · `eslint-disable` | إصلاح النوع |
| تخفيف اختبار ليمرّ | إصلاح الكود |
| `if` لانتقال حالة | XState |
| نص عربي مضمَّن | ملف ترجمة |
| رقم سحري | ثابت مُسمّى أو `thresholds` |
| `console.log` | pino |
| `Math.random()` في منطق أعمال | حقن مولّد |
| `new Date()` في المجال | حقن ساعة |

**السطران الأخيران يجعلان المجال قابلاً للاختبار الحتمي** — الاختبار يعطي نفس النتيجة ألف مرة.

## 5-4 قائمة المراجعة البشرية — لكل شريحة

| # | يُفحص | الرافض |

## 5-5 هرم الاختبار — بالأرقام

| المستوى | الأداة | التغطية | السرعة |
|---|---|---|---|
| **وحدة — المجال** | Vitest | **≥ ٩٠٪** من `domain/` | ثوانٍ |
| **خصائص — القواعد الثابتة** | fast-check | كل قاعدة ثابتة | ثوانٍ |
| **تكامل — الأوامر** | Vitest + Testcontainers | كل أمر واستعلام | دقائق |
| **عقد — API** | من OpenAPI | كل مسار | دقيقة |

| **أمن** | ZAP + Semgrep | كل نشر | دقائق |

**اختبار الطفرة هو الحكم الحقيقي على الوكيل:** يغيّر الكود عمداً ويرى هل تفشل الاختبارات. إن لم تفشل، فالاختبارات شكلية — **وهذا أكثر خطأ يرتكبه الوكيل الذكي**.

## 5-6 اختبارات الخصائص — مثال

```ts
// wms/tests/domain/stockBalance.property.test.ts
test('الرصيد يساوي مجموع الدفتر دائماً — مهما كان ترتيب الحركات', () => {
  fc.assert(fc.property(
    fc.array(movementArb()),                // آلاف التوليفات العشوائية
    (movements) => {
      const ledger  = applyAll(movements);
      const balance = rebuildBalance(ledger);
      return balance.equals(sumLedger(ledger));   // P4
    }
  ));
});
```

**هذا يختبر القاعدة على آلاف الحالات لا على ثلاث أمثلة** — وهو ما يحمي الدفاتر.
