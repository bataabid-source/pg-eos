# 2. العقد الموحّد لكل تكامل

**لا يُبنى تكامل بلا هذه الحقول التسعة معرَّفة:**

| # | الحقل | لماذا |
|---|---|---|
| 1 | مفتاح التفرّد (Idempotency Key) | يمنع معالجة نفس السجل مرتين |
| 2 | سياسة إعادة المحاولة | كم مرة · بأي تباعد · ومتى تتوقف |
| 3 | سلوك الفشل | يتوقف؟ يتخطّى ويسجّل؟ يُدخل طابور المعالجة اليدوية؟ |
| 4 | عتبة التنبيه | بعد كم فشل · لمن |
| 5 | **مالك بالمنصب** (`owner_role`) | لا تكامل بلا مالك · والشخص يُشتقّ من `identity.user_roles` — **v4 · PLT-25** |
| 6 | سجل التشغيل | `platform.integration_runs` — كل تشغيلة بنتيجتها |
| 7 | البديل اليدوي | ما يُفعل إن توقف أسبوعاً |
| 8 | تخزين الأسرار | `secret` — لا يصل المتصفح أبداً |
| 9 | مدة الاحتفاظ بالبيانات الخام | قبل الأرشفة |

## 2-1 المخطط — الحاكم في 13B

> **v4 · R-09 §4:** الـDDL التنفيذي لـ`platform.integration_config` و`platform.integration_queue` **مُعرَّف حصرياً في `A-governing/database/13B-Schema-Reference-Consolidation.sql` (القسم 13B-4)**. ما يلي مقتطف توضيحي للحقول الحاكمة فقط — **لا يُنفَّذ من هذه الوثيقة**.

```sql
-- مقتطف — التعريف الكامل في 13B §13B-4
-- platform.integration_config : العقد والسياسة (إعلان التكامل)
--   code 'I-01'…'I-11' unique · direction · transport · schedule
--   owner_role (v4 · PLT-25) · idempotency_key
--   retry_max · retry_backoff_sec · on_failure (halt · skip_log · manual_queue)
--   alert_after_failures · alert_roles[] · raw_retention_days · manual_fallback · is_active

-- platform.integration_queue : الطابور اليدوي (ما فشل ويحتاج تدخلاً بشرياً)
--   integration · payload jsonb · error · attempts
--   status (pending · resolved · discarded) · resolved_by/at/note
--   index (status, created_at)   -- الشاشة التشغيلية تقرأ pending وحدها
```

## 2-2 الثلاثة لا يتكرّرون — `config` · `queue` · `runs`

> **v4 · PLT-26 · R-07:** الجداول الثلاثة **ليست تكراراً**؛ لكل منها غرض واحد لا يؤدّيه الآخران:

| الجدول | المصدر | الغرض الوحيد | من يقرؤه |
|---|---|---|---|
| `platform.integration_config` | هذه الوثيقة §2 → 13B | **العقد والسياسة** — إعلان التكامل وحدوده وسلوكه عند الفشل. صف واحد ثابت لكل تكامل من الأحد عشر | محرّك التكاملات عند كل تشغيلة · شاشة الإعدادات |
| `platform.integration_queue` | هذه الوثيقة §2 → 13B | **الطابور اليدوي** — السجل الواحد الذي فشل ويحتاج بشراً ليبتّ فيه | شاشة الطابور · التنبيه **N-19** |
| `platform.integration_runs` | 01 | **سجل التشغيل** — كل تشغيلة بنتيجتها وعدد سجلاتها وزمنها | لوحة التكاملات · التنبيهان **N-01** و**N-22** |

**القاموس المشترك (v4 · PLT-26):** `integration_runs.integration` و`integration_queue.integration` قيمهما نصّ حرّ في 01 (`imile_agent · oula · biometric · whatsapp`). يُضاف في 13B عمود `integration_code text references platform.integration_config(code)` إلى الجدولين، وتُبذر `integration_config` بالأحد عشر رمزاً `I-01…I-11` مع `legacy_name` يطابق القيم النصية — **بدون هذا القاموس لا تُبنى لوحة التكاملات ولا التنبيه N-22**.

# 3. التفاصيل الحرجة

## I-01 · I-02 — iMile

| البند | القرار |
|---|---|
| القيد الحاكم | **جلسة واحدة فقط** — الدخول من متصفح آخر يُسقط جلسة الوكيل |
| الحساب | **حساب مخصّص للوكيل لا يستخدمه أحد** — بوصفه «وكيل محطة» بواجهة عن بُعد (40 §C8 · EXECUTION-MASTER-v4 §1.2) |
| التفرّد | `tracking_no` + `scan_type` + التاريخ |
| الفشل | ٣ محاولات · ثم طابور يدوي · تنبيه فوري لمدير التوصيل |
| التوقف > ١٥ د | تنبيه (**N-01**) · > ٦٠ د تصعيد للمدير العام |
| البديل اليدوي | تصدير CSV من البوابة ورفعه — **يُختبر مرة شهرياً** |
| **الحل الجذري** | **طلب واجهة برمجية رسمية من iMile** — يلغي الوكيل. **v4:** الطلب **يصوغه `pg-scribe` في المرحلة 3** (نصّ الطلب التقني: نقاط النهاية المطلوبة · التفرّد · المعدّل · الأمن)، و**يرسله المدير العام (GM)** بتوقيعه. لا API قبل ورود ردّ رسمي — الوكيل يبقى المسار الوحيد حتى ذلك الحين. |

## I-04 — تطبيق البصمة

| البند | القرار |
|---|---|
| العطل القائم | `ATTEND_EMAIL` / `ATTEND_PASS` غير مخزّنة · لا مُشغّل تلقائي |
| **تُدخل بيدك** | كلمات المرور لا يُدخلها أحد نيابة عنك — **مع ضابط الأربع أعين (§5)** |
| التفرّد | `employee_id` + الختم الزمني للبصمة |
| المطابقة | رقم الموظف — غير المطابق إلى طابور يدوي **لا يُهمل** |
| الصور | Firebase · حذف بعد ٦٠ يوماً بقاعدة دورة حياة |
| ⚠️ حاجز | **لا يُفعَّل الرصد الآلي للغياب والتأخير قبل اكتمال بيانات الحضور ≥ ٩٥٪ لمدة ٣٠ يوماً متصلة** (EXECUTION-MASTER-v4 §1.3) — التفعيل على بيانات ناقصة يولّد مئات الجزاءات الخاطئة. العلم في `platform.feature_flags`. **v4 · PLT-50** |

## I-03 — أولى (بطاقات الوقود)

| البند | القرار |
|---|---|
| الواقع | **لا واجهة برمجية لدى أولى** — التعديل على البوابة يدوي |
| المسار | تصدير من البوابة → استيراد CSV → مطابقة بالبطاقة والمركبة |
| التفرّد | (رقم البطاقة + التاريخ + المبلغ) |
| الضابط | **قراءة العداد إلزامية** مع كل تعبئة · انحراف > ٢٠٪ عن معدل المركبة → تنبيه وتحقيق |
| بطاقة لموظف غادر | حاجز صلب — إخلاء الطرف يلغي البطاقة آلياً |

## I-05 · I-06 — واتساب والرسائل النصية (Twilio)

| الاستخدام | القاعدة |
|---|---|
| المزوّد | **Twilio** للقناتين: WhatsApp Business API (I-05) و SMS (I-06) — **v4 · PLT-27** |
| **القوالب** | **T1–T5 معرَّفة في وثيقة 35 §1-3** — هذه الوثيقة تحيل إليها ولا تكرّرها. **لا كتابة حرة إطلاقاً.** |
| تأكيد الطلب قبل التوزيع | قالب معتمد |
| رابط تتبّع + إثبات تسليم | بعد الإقفال (T5) |
| تنبيه السائق بمهمة جديدة | — |
| **ما لا يُرسل أبداً** | أسعار · بيانات عميل آخر · أي حقل مصنَّف `commercial` أو `payroll` |
| الحدود | سقف يومي لكل عميل · **ساعات هدوء ٢٢:٠٠–٠٧:٠٠** عدا الطوارئ (وثيقة 25 §1) |
| الفشل | ارتداد إلى الرسائل النصية (I-06) ثم إلى مهمة للكول سنتر · نسبة الارتداد > ٥٪ = تنبيه **N-20** |

> **القوالب الخمسة (المصدر الوحيد: 35 §1-3):** T1 عند الخروج · T2 عند الوصول · T3 بعد محاولتين · T4 رابط الدفع · T5 بعد الإقفال. أي تعديل عليها يُجرى في **35** لا هنا.

## I-08 — البنك

| البند | القرار |
|---|---|

## I-09 — واجهة العملاء (نحن المزوّد)

```
POST /api/v1/orders            إنشاء أمر — مفتاح تفرّد إلزامي من العميل
GET  /api/v1/orders/{ref}      حالة الأمر
GET  /api/v1/inventory         رصيده هو فقط
GET  /api/v1/shipments/{no}    تتبّع
POST /api/v1/webhooks          تسجيل نقطة استقبال أحداثه
```
| الضابط | القاعدة |
|---|---|
| المصادقة | مفتاح لكل عميل · قابل للإبطال فوراً |
| العزل | **RLS في القاعدة** — لا في الكود |
| الحد | ١٠٠ طلب/دقيقة لكل عميل |
| التفرّد | `client_ref` فريد لكل عميل — إعادة الإرسال لا تنشئ أمراً ثانياً |
| الإصدار | `/v1` ثابت · التغيير الكاسر يفتح `/v2` ويبقى `/v1` ٦ أشهر |

# 4. المراقبة — ستة مؤشرات، أربعة منها تنبيهات مرقَّمة

> **v4 · PLT-12 · R-07:** المؤشران الأولان كانا موجودين في سجل 25 (N-01 · N-16). **الأربعة الباقية تصير تنبيهات مرقَّمة N-19…N-22** في وثيقة 25 §2 — فالعدد المعتمد صار **٢٢ تنبيهاً**، وتُبنى جميعها في مهمة 5.13.

| المؤشر | العتبة | الإجراء | رمز التنبيه (25 §2) |
|---|---|---|---|
| وكيل iMile متوقف | > ١٥ دقيقة | تنبيه فوري · > ٦٠ د تصعيد | **N-01** |
| مزامنة البصمة فاشلة | يومان متتاليان | تنبيه | **N-16** |
| طابور المعالجة اليدوية | > ٢٠ سجلاً أو عمر > ٤٨ ساعة | تنبيه لمالك التكامل | **N-19** ✳ v4 |
| رسائل واتساب مرتدّة | > ٥٪ | مراجعة القوالب (35 §1-3) | **N-20** ✳ v4 |

| أي تكامل بلا تشغيل ناجح | ٢٤ ساعة | تنبيه لمالك التكامل | **N-22** ✳ v4 |

**لوحة التكاملات:** صف لكل تكامل — آخر تشغيل ناجح · عدد السجلات · الفشل · الطابور اليدوي · المالك. **صف واحد أحمر = يوم لا يُقفل.**
مسار الشاشة: `/platform/integrations` (وثيقة 29 §6-3 · فئة «إعدادات وإدارة»).

# 5. الأسرار

| القاعدة | التطبيق |
|---|---|
| التخزين | مدير أسرار أو متغيرات بيئة — **لا في الكود ولا في قاعدة البيانات نصاً** |
