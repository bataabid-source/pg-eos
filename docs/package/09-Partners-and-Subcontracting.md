# 1. المشكلة

بريميوم تبيع خدمة لعميلها، ويقدّمها **طرف ثالث**:

| الحالة | المثال |
|---|---|
| تخزين لدى الغير | مخزن بريميوم ممتلئ → بضاعة العميل في مخزن شريك |
| توصيل بالباطن | حجم يفوق الأسطول → شركة توصيل شريكة تنفّذ |
| نقل ثقيل | حاوية تحتاج معدات لا نملكها |
| كول سنتر إضافي | ذروة موسمية تتجاوز المقاعد |
| مناولة متخصّصة | عمالة متعاقدة لمشروع محدد |

**بدون تصميم لهذا:**
- التكلفة لا تُربط بالعميل → **الربحية خاطئة بالكامل**
- فاتورة الشريك تُدخل يدوياً → لا مطابقة مع ما قُدِّم فعلاً
- العميل يشتكي والمسؤولية غير واضحة
- لا أحد يعرف هامش الخدمة المعاد بيعها

# 2. المبدأ الحاكم

```
العميل يرى بريميوم وحدها. الشريك لا يظهر ولا يفوتر العميل مباشرة أبداً.
```

| القاعدة | لماذا |
|---|---|
| **الشريك لا يُسمَّى للعميل** — قرار مُغلق (EXEC §1.1) | العلاقة والمسؤولية والسمعة لنا؛ ونافذة العميل لا تكشف منفّذ الخدمة إطلاقاً، ولا في تفاصيل الشحنة ولا في كشف المخزون |
| **بريميوم هي المتعاقد الوحيد مع العميل** | العلاقة والمسؤولية والسمعة لنا |
| الشريك يفوتر بريميوم · بريميوم تفوتر العميل | الفرق = هامشنا · وهو مقياس النجاح |
| **كل حدث خدمة معاد بيعها يحمل `partner_id`** | بدونه التكلفة لا تُربط بالعميل |
| **SLA ظهر لظهر** (Back-to-Back) | التزام الشريك لنا ≥ التزامنا للعميل — وإلا تحمّلنا غرامة بلا تعويض |
| فاتورة الشريك تُطابَق بالأحداث آلياً | يمنع دفع ما لم يُقدَّم |

# 3. أنواع علاقات الشركاء

| النوع | الوصف | الفوترة |
|---|---|---|
| **إعادة بيع** (Resale) | نشتري بسعر ونبيع بسعر أعلى | فاتورة شريك (مدين) · فاتورة عميل (دائن) |
| **سعة محجوزة** (Committed) | نحجز سعة ثابتة شهرياً سواء استُخدمت أو لا | التزام ثابت — **أخطر نوع** |
| **بالطلب** (On-Demand) | عند الحاجة فقط بسعر متفق | متغيّر بالكامل |
| **عمولة** (Agency) | نوجّه العمل للشريك ونأخذ عمولة | إيراد عمولة فقط · لا تكلفة |
| **عمالة متعاقدة** (Manpower) | عمالة من مورّد تعمل في مواقعنا | تكلفة عمالة غير مباشرة |

**تحذير على «السعة المحجوزة»:** إن حجزت 200 منصة لدى شريك واستخدمت 80، فالـ120 خسارة صافية. النظام يجب أن ينبّه على **نسبة الاستغلال** شهرياً، وأي حجز تحت 70% ثلاثة أشهر يُراجَع.

# 4. المخطط — جداول الشركاء

> **التعريف الحاكم في `A-governing/database/13B-Schema-Reference-Consolidation.sql`.** ما يلي وصف الجداول ومعنى أعمدتها الحاكمة فقط — **لا يُبنى منه DDL**، لأن نسخة الوثيقة تنحرف عن المخطط المطبَّق مع كل تعديل.

| الجدول | الغرض | الأعمدة الحاكمة |
|---|---|---|
| `partners.partners` | سجل الشركاء والموردين | `code` · `partner_type` (`warehouse · delivery · transport · cc · manpower · other`) · `payment_terms_days` · `rating` (من نتائج SLA) · `status` |
| `partners.partner_contracts` | عقد الشريك | `relation_type` (`resale · committed · on_demand · agency · manpower`) · `committed_qty`/`committed_monthly_cost` · **`min_utilization_pct`** · `sla_back_to_back` · **`penalty_recoverable`** · **`liability_cap`** · **`insurance_by`** · `insurance_expiry` · `audit_right` |
| `partners.partner_price_lines` | ملحق أسعار الشريك — **ما ندفعه نحن** | `service_id` → `catalog.services` · `cost_price` · شرائح `tier_from`/`tier_to` · `valid_from`/`valid_to` |
| `partners.service_allocations` | من ينفّذ ماذا لمن | `client_id × service_id × partner_id` · `location_scope` · `priority` عند تعدّد الشركاء لنفس الخدمة · نافذة صلاحية |
| `partners.payable_events` | **نظير `billing.billable_events` تماماً** | `client_id` (أساس الربحية) · `service_id` · `qty`/`cost_price`/`amount` · **`billable_event_id`** (الرابط الذي يجعل الهامش فورياً) · `status` (`pending · priced · matched · invoiced · disputed`) |
| `partners.partner_invoices` | فاتورة الشريك الواردة | `partner_ref` (رقمه) مقابل `doc_no` (ترقيمنا) · `claimed_amount` · `matched_amount` · `variance_amount` (مولَّد) · `approved_amount` · **`matched_by` ≠ `approved_by`** · `status` |
| `partners.resale_margin` | عرض هامش الخدمة المعاد بيعها | يشتق الهامش من ربط `payable_events.billable_event_id` بـ`billing.billable_events` |

**مقتطف الأعمدة التي يتوقف عليها نصّ هذه الوثيقة** (صيغة مختصرة للقراءة — الصيغة الكاملة في 13B):

```sql
-- partners.partner_contracts (مقتطف)
  min_utilization_pct     numeric(5,2),   -- §3: أي حجز تحت 70% ثلاثة أشهر يُراجَع
  sla_back_to_back        boolean not null default false,
  penalty_recoverable     boolean not null default false,  -- §7: إلزامي في كل عقد جديد
  liability_cap           numeric(14,3),  -- §7-1: min(3 × الفوترة الشهرية، قيمة العقد)
  insurance_by            text,           -- §7-1 · §10-7: 'partner'
  audit_right             boolean not null default true,   -- §8: حق الجرد التعاقدي

-- partners.payable_events (مقتطف)
  client_id               uuid references sales.accounts(id),  -- بدونه التكلفة لا تُربط بالعميل
  billable_event_id       uuid references billing.billable_events(id),

-- partners.partner_invoices (مقتطف)
  variance_amount         numeric(14,3) generated always as (claimed_amount - matched_amount) stored,
  matched_by              uuid,
  approved_by             uuid,
  -- ضابط أدنى حتى يُحسم معتمِد فاتورة الشريك (§10 البند 3):
  -- constraint matcher_ne_approver check (matched_by is null or approved_by is null or matched_by <> approved_by)
```

**أعمدة يُضيفها v4** (مسجَّلة في `_changelog/ADM-SCHEMA-NEEDS.md` لوكيل المخطط): `partner_contracts.liability_basis text` — الأساس الذي حُسب منه السقف (`3x_monthly` أو `contract_value`) وتاريخ الحساب.

# 5. مسار العمل — من الخدمة إلى الدفع

```
① تخصيص: العميل × الخدمة × الشريك (service_allocations)
       ▼
② العميل يطلب الخدمة → أمر في النظام كالمعتاد
       ▼
③ التنفيذ:
   · لدينا  → حركاتنا العادية
   · لدى الشريك → أمر خدمة للشريك + متابعة تنفيذه
       ▼
④ إقفال العملية → حدثان متزامنان:
       billable_event  (نبيع للعميل بسعر العقد)
       payable_event   (ندفع للشريك بسعر التعاقد)
       مرتبطان بمفتاح واحد ← الهامش يُحسب فوراً
       ▼
⑤ نهاية الشهر:
   · فاتورتنا للعميل تصدر كالمعتاد
   · فاتورة الشريك تُستلم وتُطابَق آلياً بأحداثنا
       ▼
⑥ المطابقة (العتبة: partner.match_tolerance_pct = 2%):
   · الفرق ≤ 2%          → اعتماد آلي للدفع
   · الفرق > 2% بالزيادة → 🚩 تجميد الدفع → بند قرار → نزاع موثّق
   · الشريك يطالب بأقل   → 🚩 تنبيه (ربما لم نستلم كل الخدمة)
       ▼
⑦ الاعتماد والدفع → قيد: مدين 5xxx مصروف شريك | دائن 2100 ذمم موردين
```

## 5-1 المطابقة الآلية — أهم ضابط في الوثيقة

**بدونها تدفع لما لم يُقدَّم.** النظام يطابق فاتورة الشريك بأحداثنا المسجّلة:

**العتبة الحاكمة:** `platform.thresholds['partner.match_tolerance_pct']` — القيمة المطبَّقة **2%** (40 §C6 · 29 §5-3 · 12 س20). وهي **عتبة واحدة** تحكم الاعتماد الآلي والتجميد معاً؛ لا وجود لعتبة «تطابق 100%» منفصلة.

| النتيجة | الإجراء |
|---|---|
| **فرق ≤ 2%** (بما فيه التطابق التام) | **اعتماد آلي** — `auto-approve` بلا تدخل بشري |
| **فرق > 2%** | **تجميد الدفع** · تقرير سطر بسطر · **بند في صندوق القرارات** · نزاع موثّق |
| بند في فاتورة الشريك بلا حدث لدينا | **مرفوض** — لا دفع بلا إثبات، مهما صغر المبلغ |
| حدث لدينا بلا بند في فاتورته | تنبيه — قد يكون خصماً مستحقاً أو خدمة لم تُقدَّم |

> **مُثبَّت في v4:** `partner.match_tolerance_pct = 2` مسجَّل في EXECUTION-MASTER-v4 §1.1 (Partner invoice matching tolerance) — القيمة 2% متطابقة في 40 §C6 و29 §5-3 و12 س20.

# 6. الربحية — التغيير الجوهري

## قبل إضافة الشركاء (خاطئ)
```
هامش العميل = الإيراد − (رواتبنا + وقودنا + مساحتنا)
```
الخدمة المقدَّمة من شريك تظهر **بلا تكلفة** → هامش وهمي مرتفع.

## بعد الإضافة (صحيح)
```
هامش العميل = الإيراد
            − التكلفة المباشرة (عمالة · وقود · مساحة · مركبات)
            − تكلفة الشركاء (من payable_events مربوطة بالعميل)
            − غرامات SLA
```

| مؤشر جديد | ما يكشفه |
|---|---|
| **هامش الخدمة المعاد بيعها** | لكل خدمة × شريك |
| نسبة الخدمات المُسندة للشركاء | اعتماد مفرط = خطر |
| **نسبة استغلال السعة المحجوزة** | ما ندفعه ولا نستخدمه — خسارة صافية |
| تكلفة الشريك لكل عميل | عميل يبدو مربحاً وهو ليس كذلك |

# 7. المسؤولية وSLA

```
العميل ──── SLA (التزامنا له) ────► بريميوم ──── SLA ظهر لظهر ────► الشريك
   ▲                                                                    │
   └────────── الشكوى تأتي إلينا نحن دائماً ◄───────────────────────────┘
```

| القاعدة | لماذا |
|---|---|
| **التزام الشريك ≥ التزامنا للعميل** | وإلا تحمّلنا الغرامة بلا استرداد |
| الغرامة قابلة للاسترداد من الشريك | `penalty_recoverable = true` — وإلا فالخسارة علينا |
| الشكوى تُفتح على بريميوم دائماً | العميل لا يعرف الشريك ولا يتعامل معه |
| تذكرة داخلية موازية للشريك | متابعة الحل — ويقاس زمن استجابته |
| تقييم الشريك ربعياً | من نتائج SLA ونسب النزاع والفروق |
| **سقف المسؤولية** | **`liability_cap = min(3 × الفوترة الشهرية للشريك، قيمة العقد)`** — القاعدة المحسومة في EXEC §1.1 · **والتأمين على الشريك** (`insurance_by = 'partner'`) |

## 7-1 سقف المسؤولية — القاعدة والفجوة التي تبقى

**القاعدة المحسومة (EXEC §1.1 — تحكم عند التعارض):**

```
liability_cap = min(3 × monthly billing, contract value)
insurance_by  = partner
```

وهي صيغة **ظهر لظهر قياسية**، وقيمتها **قد تقلّ عن التزامنا للعميل**. ولذلك يبقى نصّ الحذر التالي قائماً — لا كقاعدة بديلة بل كإجراء رقابي:

**نقطة حذر قانونية:** لو حدّد الشريك سقف مسؤوليته بـ 1,000 د.ك، والتزامنا للعميل 10,000، فالفرق علينا. **هذا يُراجَع قبل توقيع أي عقد شريك.**

**كيف يُفرض الحذر بلا مخالفة القاعدة المحسومة:** `liability_cap` عمود مفرد لا يسع صيغة `min(...)`، فيُخزَّن فيه **الناتج المحسوب** ويُضاف `liability_basis text` يحمل الأساس الذي حُسب منه (`3x_monthly` أو `contract_value`) وتاريخ الحساب. ثم:

| الضابط | السلوك |
|---|---|
| **تنبيه انكشاف** لا اشتراط تعاقدي | عند `liability_cap < مجموع تعرّضنا لغرامات SLA على العملاء المخدومين بهذا الشريك` → تنبيه للمدير المالي وبند في ملف تجديد عقد الشريك |
| إعادة الحساب | آلياً عند كل تغيّر في الفوترة الشهرية أو قيمة العقد |
| الاستثناء | سقف أعلى من القاعدة يُقبل دائماً؛ وأدنى منها يحتاج قرار `GM` مسجَّلاً |

> السبب: «ألا يقل عن التزامنا للعميل» اشتراط **غير قابل للفرض** — لا نملك إجبار الشريك عليه، ولا يمكن التحقق منه آلياً وقت التوقيع. أما التنبيه على الانكشاف فقابل للقياس والفرض.

# 8. حالة خاصة — تخزين لدى الغير

| البند | المعالجة |
|---|---|
| المخزن | يُسجَّل كـ `warehouse` بعلامة `is_partner = true` ومربوط بالشريك |
| المواقع | **لا نرقّمها نحن** — نستخدم ترقيم الشريك ونخزّنه كمرجع خارجي |
| الرصيد | نمسك الرصيد لدينا · **مطابقة دورية إلزامية مع كشف الشريك** |
| الجرد | حق جرد تعاقدي — بند إلزامي في عقد الشريك |
| التأمين | من يؤمّن البضاعة؟ **يجب النص صراحةً** |
| نافذة العميل | يرى مخزونه و**لا يرى أنه لدى شريك** — الشريك لا يُسمَّى للعميل (EXEC §1.1) |
| الصرف | أمر صرف لدينا → أمر للشريك → إثبات منه |

**أخطر بند: مطابقة الرصيد.** اختلاف رصيدنا عن رصيد الشريك يعني مسؤولية مالية غامضة. **مطابقة أسبوعية إلزامية**، وأي فرق يُصعَّد خلال 48 ساعة.

# 9. حالة خاصة — توصيل بالباطن

| البند | المعالجة |
|---|---|
| الشحنات | تُنشأ لدينا · تُسند للشريك بعلامة `executed_by_partner` |
| إثبات التسليم | **بنفس معاييرنا: GPS + توقيع/صورة + اسم المستلم** — لا تنازل |
| المتابعة | حالة لحظية من الشريك (API أو رفع ملف أو إدخال) |
| COD | **الأخطر** — الشريك يحصّل نقداً · مطابقة يومية إلزامية · تأمين أو ضمان |
| المرتجعات | إلى مستودعنا لا مستودع الشريك |
| الفوترة | نفوتر العميل بسعرنا · يفوترنا الشريك بسعره |

**قاعدة إلزامية:** **لا تنازل عن معيار إثبات التسليم.** شريك لا يستطيع تقديم POD بمعاييرنا لا يُسند له عمل — لأن النزاع سيقع علينا ولن نملك دليلاً.

# 10. القرارات — الحالة في v4

| # | القرار (كما طُرح في v1) | الحالة · القيمة المحسومة |
|---|---|---|
| 1 | هل يُذكر الشريك للعميل؟ | **مُغلق** — **لا**. الشريك لا يُسمَّى للعميل في أي شاشة أو مستند (EXEC §1.1 · §2 · §8) |
| 2 | حد الهامش الأدنى على الخدمة المعاد بيعها | **ما زال مفتوحاً** — `[GM DECISION REQUIRED: الحد الأدنى لهامش الخدمة المعاد بيعها. حدّ الهامش العام 15% تحذير / <10% GM (EXEC §1.1) موضوع للعقد ككل لا للخدمة المعاد بيعها منفردةً؛ وبيع خدمة شريك بهامش سالب ممكن اليوم بلا حارس]` |
| 3 | من يعتمد فاتورة الشريك ومن يطابقها؟ | **ما زال مفتوحاً** — `[GM DECISION REQUIRED: تسمية دورَي المطابقة والاعتماد لفاتورة الشريك. لا زوج SoD يغطيه في EXECUTION-MASTER-v4 §1.6، و40 §C6 يصف المطابقة الآلية بلا تسمية دورين؛ فقد يكون `matched_by` و`approved_by` الشخص نفسه]`. **الضابط الأدنى المطبَّق حتى الحسم:** قيد `matcher_ne_approver` يمنع أن يكون المطابِق هو المعتمِد |
| 4 | حد الفرق المقبول في المطابقة | **مُطبَّق بقيمة 2%** (§5-1) — وغير مسجَّل في EXEC؛ انظر التنويه في §5-1 |
| 5 | سياسة السعة المحجوزة: الحد الأدنى لنسبة الاستغلال | **مطبَّق بقيمة 70%** (§3): أي حجز تحت 70% ثلاثة أشهر متتالية يُراجَع. العمود `partner_contracts.min_utilization_pct` قائم. **غير مسجَّل في EXEC** — يُسجَّل كما هو ولا يُغيَّر |
| 6 | هل غرامات SLA قابلة للاسترداد من الشركاء؟ | **مُغلق** — **نعم**، `penalty_recoverable = true` **بند إلزامي في كل عقد شريك جديد**؛ وأي عقد بدونه يحتاج قرار `GM` مسجَّلاً |
