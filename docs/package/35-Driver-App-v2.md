# 1. الاتصال بالعميل من داخل التطبيق

## 1-1 ثلاث قنوات — وقاعدة واحدة حاكمة

> **القاعدة الحاكمة مقيَّدة زمنياً (v4 — OPS-37):**
> - **عند `masked` (من نهاية المرحلة 3):** الرقمان مخفيان — رقم السائق لا يظهر للعميل، ورقم العميل لا يُخزَّن في الجهاز.
> - **عند `direct` (الوضع الافتراضي عند الإطلاق):** **رقم العميل لا يُخزَّن في جهاز السائق**، لكن **رقم السائق قد يظهر لهوية المتصل** — **يُبلَّغ السائق بذلك كتابةً ويُدرج في عقد العمل**.
>
> الصيغة المطلقة السابقة («لا يظهر أبداً») كانت **وعداً غير قابل للوفاء طوال المراحل 0–3** لأن `direct` هو الوضع المعتمد عند الإطلاق (EXEC §1.2)، والتزام تعاقدي لا يغطيه التصميم.

| القناة | الآلية | الأثر |
|---|---|---|
| **مكالمة** | **رقم وسيط (Number Masking)** — الخادم يربط الطرفين | الرقمان مخفيان · المكالمة مسجَّلة المدة |
| **واتساب** | رابط `wa.me` برسالة قالب معتمد مسبقاً | لا كتابة حرة |
| **رسالة نصية** | تُرسل من الخادم لا من جهاز السائق | لا تظهر في جواله |

**لماذا الرقم الوسيط:** بدونه يحتفظ العميل برقم السائق ويتصل به خارج العمل، ويتحوّل السائق إلى قناة خدمة غير مراقَبة. وفي الاتجاه الآخر، السائق يحتفظ بأرقام العملاء بعد مغادرته.

## 1-2 قرار التصميم — طبقة إخفاء قابلة للتركيب

**القرار المعتمد: يُبنى التطبيق ليقبل مزوّد رقم وسيط — بلا إلزام بتعاقد الآن.**

```
طبقة الاتصال (ثابتة)
      ▼
واجهة المزوّد (Adapter)
      ├── direct   ← الوضع الافتراضي عند الإطلاق
      └── masked   ← يُفعَّل بتبديل إعداد عند التعاقد
```

| الوضع | السلوك | متى |
|---|---|---|
| `direct` | اتصال مباشر · **الرقم يُطلب من الخادم لحظياً ولا يُخزَّن في الجهاز** | الإطلاق |
| `masked` | رقم وسيط يربط الطرفين | عند التعاقد مع مزوّد |

**ما يبقى ثابتاً في الوضعين:**
- كل اتصال يمرّ بالخادم ويُسجَّل في `contact_log`
- الرقم لا يُحفظ في جهات اتصال الجهاز
- التبديل **إعداد في `platform.settings`** — لا تعديل كود ولا إصدار جديد

> بهذا تحصل على الفائدة الأمنية فوراً (لا تخزين أرقام)، وتؤجّل التكلفة (المزوّد) بلا إعادة بناء.

## 1-3 قوالب الرسائل T1–T5 — **معرَّفة هنا، و23 تحيل إليها** (v4)

| # | القالب | متى | الحالة عند الإطلاق |
|---|---|---|---|
| T1 | «شحنتك في الطريق · الوصول خلال ٣٠ دقيقة تقريباً» | عند الخروج | مفعّل |
| T2 | «وصلت لموقعك · أنا بانتظارك» | عند الوصول | مفعّل |

# 2. الدفع التفاعلي

## 2-1 آلة حالات الدفع — الثغرة الأخطر

> **القاعدة غير القابلة للتفاوض: تأكيد الدفع يأتي من بوابة الدفع أو من عدّ النقد — لا من قول السائق.**

```
غير مدفوع
   ├── نقداً ──► السائق يؤكد الاستلام ──► «محصَّل — بانتظار التوريد»
   │                                          └──► توريد بمسح إيصال المحاسب ──► مسوّى
   └── رابط ──► يُولَّد ويُرسل ──► بانتظار الدفع
                                      ├── البوابة تؤكد ──► مدفوع ✓
                                      ├── انتهت المهلة ──► يُعاد التوليد
                                      └── رفض ──► تحوّل للنقد أو فشل
```

| الضابط | السلوك |
|---|---|
| **الرابط غير المدفوع لا يسمح بالتسليم** | زر «سُلِّم» معطّل حتى تأكيد البوابة |
| التأكيد لحظي | إشعار فوري للسائق عند الدفع |
| **دفع جزئي** | ⛔ **مرفوض مطلقاً** — لا استثناء ولا اعتماد مشرف · المبلغ كاملاً أو فشل |
| مبلغ مختلف | يُرفض — المبلغ من النظام لا من السائق |
| رابط منتهٍ | يُعاد توليده بضغطة · الرابط القديم يُبطَل |
| **بلا شبكة** | **الرابط غير متاح** — النقد فقط · ويُعلَم السائق بوضوح |

```sql
create table tms.payment_attempts (
  id uuid primary key default gen_random_uuid(),
  task_id uuid not null references tms.delivery_tasks(id),
  method text not null,              -- cash · link · pos
  amount_due numeric(14,3) not null,
  amount_paid numeric(14,3),
  link_url text, link_expires_at timestamptz,
  gateway_ref text, gateway_status text,
  confirmed_at timestamptz,
  confirmed_by text,                 -- gateway · driver_cash · supervisor
  created_at timestamptz not null default now(),
  constraint link_needs_gateway check (
    method <> 'link' or confirmed_at is null or gateway_ref is not null)
);
```

**القيد الأخير هو الحارس:** الدفع بالرابط لا يُعتبر مؤكَّداً بلا مرجع من البوابة. **مستحيل برمجياً أن يعلن السائق دفعاً إلكترونياً لم يحدث.**

## 2-3 قرار التصميم — بوابة الدفع لاحقاً

**القرار المعتمد: الربط مع مزوّد بوابة الدفع يتم لاحقاً.**

```
محرّك الدفع (ثابت)
      ▼
واجهة البوابة (Adapter)
      ├── none        ← الإطلاق (النقد فقط)
      └── <المزوّد>    ← يُفعَّل بإعداد عند التعاقد
```

> **v4 (OPS-36): القيمة الافتراضية اسمها `none` لا `cash_only`** — مطابقةً لـ40 §C4 (`driver.payment.gateway = none|<provider>`) وللإعداد المبذور في §12-1. القيمتان كانتا تسميتين لشيء واحد وهو ما يكسر أي مقارنة آلية.

| البند | الإطلاق | بعد التعاقد |
|---|---|---|
| النقد | ✅ يعمل كاملاً | ✅ |
| رابط الدفع | 🔒 **مخفي في التطبيق** | ✅ يظهر |
| القالب T4 | غير مفعّل | مفعّل |
| جدول `payment_attempts` | **يُبنى من الآن** بحقول البوابة | يُستخدم |

**قاعدة:** البنية تُبنى كاملة من اليوم الأول، والميزة تُخفى بمفتاح. **إضافة البوابة لاحقاً تعديل إعداد لا إعادة بناء.**

# 3. مسح الشحنة للتسليم — حاجز صلب

| القاعدة | |
|---|---|
| **لا تسليم بلا مسح الباركود** | يمنع تسليم شحنة لشخص آخر |
| الباركود لا يُقرأ | إدخال آخر ٦ أرقام يدوياً + **يُعلَّم للتدقيق** |
| مسح شحنة ليست في عهدته | ⛔ رفض فوري |
| مسح شحنة مُسلَّمة | ⛔ «سُلِّمت الساعة ١١:٤٧» |
| **مسح متأخر** | المسح بعد أكثر من ٥ دقائق من «وصلت» → يُعلَّم |

**الإحصاء المستهدف:** ≥ ٩٨٪ من التسليمات بمسح فعلي. أي سائق تحت ٩٠٪ يُراجَع.

# 4. شجرة أسباب الفشل — مستويان

**قائمة مغلقة تماماً. لا خيار «أخرى» بنص حر.**

| السبب الرئيسي | الأسباب الفرعية | إلزامي معها |
|---|---|---|
| **لا يوجد رد** | لم يرد على الهاتف · الهاتف مغلق · الرقم خطأ · لم يفتح الباب | **محاولتا اتصال مسجَّلتان** |
| **العنوان** | غير صحيح · غير مكتمل · لم أجد المبنى · منطقة خارج التغطية | ما وجده فعلاً + 📍 |
| **المستلم** | رفض الاستلام · طلب التأجيل · غير موجود · غير مخوّل | سبب من العميل |
| **الدفع** | المبلغ غير متوفر · رفض الدفع · يريد دفعاً مختلفاً | الموعد البديل |
| **الشحنة** | تالفة · ناقصة · غير مطابقة للطلب | **📷 صورة إلزامية** |
| **الوصول** | منطقة مغلقة · منع أمني · طريق مسدود · ظرف جوي | 📷 |
| **السائق** | عطل مركبة · حادث · نفاد وقت الوردية | تبليغ المشرف فوراً |

**الأثر التصميمي:** ٧ رئيسية و**٢٥ سبباً فرعياً محدداً** بدل «فشل التوصيل». هذا ما يحوّل الفشل من رقم إلى **قائمة معالجة**: ٤٠٪ عنوان → مشروع تطبيع العناوين · ٣٠٪ لا رد → تأكيد مسبق (CC-08).

> **العدد الصحيح 25 لا 24** (v4 — OPS-33). العدّ من الجدول أعلاه: لا يوجد رد **4** · العنوان **4** · المستلم **4** · الدفع **3** · الشحنة **3** · الوصول **4** · السائق **3** = **25**. الرقم «24» يُصحَّح في 35 §11 وفي 40 §C4 (`failure_reasons (7 parents × 25 children)`). **أي بذرة مبنية على 24 تُسقط سبباً.**

## 4-1 التصنيف المعتمد — أي الأسباب تُحتسب على السائق

| السبب الفرعي | تُحتسب؟ | الشرط |
|---|---|---|
| لم يرد على الهاتف | ❌ | — |
| الهاتف مغلق · الرقم خطأ | ❌ | — |
| **لم يفتح الباب** | ⚠️ **مشروط** | تُحتسب **إن لم توجد محاولتا اتصال مسجَّلتان** |
| العنوان غير صحيح · غير مكتمل | ❌ | مسؤولية بيانات العميل |
| **لم أجد المبنى** | ⚠️ **مشروط** | تُحتسب إن كان الموقع المسجَّل **> ٣٠٠ م** عن العنوان |
| خارج التغطية | ❌ | — |
| رفض الاستلام · طلب التأجيل · غير موجود · غير مخوّل | ❌ | — |
| المبلغ غير متوفر · رفض الدفع · يريد دفعاً مختلفاً | ❌ | — |
| الشحنة تالفة · ناقصة · غير مطابقة | ❌ | مسؤولية المستودع |
| منطقة مغلقة · منع أمني · طريق مسدود · ظرف جوي | ❌ | — |
| **عطل مركبة** | ❌ | **لا تُحتسب على السائق في `counts_against_driver`** — تُعالَج في **مسار الأسطول**؛ وإن ثبت الإهمال فهو **إجراء انضباطي مستقل بالبند `VEH-07`** لا خصم على تقييم التوصيل (v4 — OPS-32) |
| **حادث** | ❌ | **لا تُحتسب على السائق** — تُعالَج في **مسار التحقيق**؛ **لا تحميل إلا بعد تحقيق، وبسقف تحمّل التأمين** (EXEC §1.3)، وإن ثبت فهو البند `VEH-04` (v4 — OPS-32) |
| **نفاد وقت الوردية** | ✅ **تُحتسب** | سوء إدارة وقت — إلا بتجاوز مشرف |

**الخلاصة: ٣ أسباب فقط تُحتسب على السائق من ٢٥** — `no_answer.door_not_opened` · `address.building_not_found` · `driver.shift_time_exhausted`.

> **ما تغيّر في v4 (OPS-32):** كان الجدول يعلّم **خمسة** صفوف بـ⚠️/✅ بينما الخلاصة تقول «ثلاثة»، و40 §C4 يذكر ثلاثة، وEXEC §1.2 يعلّم البند **FIXED** ومربوطاً نصاً بـ«الثلاثة في 35 §4-1». نُقل «عطل مركبة» و«حادث» إلى ❌ لأن نسبتهما إلى السائق تتطلب **تحقيقاً** لا قاعدة آلية — وهو ما يناقض المبدأ المكتوب أسفل الجدول نفسه: «المشروط يُقرّره النظام آلياً من سجل الاتصال وبيانات الموقع — لا برأي المشرف». وكلاهما يبقى مساراً إدارياً كاملاً في الأسطول/التحقيق، ولا يضيع.

| القاعدة | |
|---|---|
| **العبء على النظام لا على السائق** | السبب لا يُحتسب إلا بدليل — لا بافتراض |
| المشروط يُقرّره النظام آلياً | من سجل الاتصال وبيانات الموقع — لا برأي المشرف |
| **التجاوز اليدوي** | للمشرف فقط · **بسبب مسجَّل** · يظهر في تقرير شهري |
| المراجعة | كل ٦ أشهر — أي سبب يُحتسب على > ٣٠٪ من السائقين **يُراجَع تصنيفه** |
| **العلاقة بـ`driver_trust`** | نسبة الفشل المنسوب للسائق هي المكوّن `p2` بوزن **0.25** في ADR-28 — و**`driver_trust` لا يُربط بأجر ولا بجزاء** (§8-4) |

> القاعدة الأخيرة تحمي من الظلم الجماعي: إن كان نصف السائقين «ينفد وقتهم»، فالمشكلة في حجم المسارات لا في السائقين.

## 8-3 قرار التصميم — خيار بيد الإدارة

**القرار المعتمد: الترتيب بين الزملاء خيار تتحكم فيه الإدارة — لا ثابت في التطبيق.**

```sql
-- ⚠️ v4 (OPS-34 · R-06): `on conflict do nothing` لا يعمل مع entity_id = null.
--    القيد الفريد هو settings_entity_id_key_key UNIQUE (entity_id, key)، وقيم NULL
--    متمايزة افتراضياً في PostgreSQL 16 — فلا يتطابق أي صف، وإعادة تشغيل الهجرة
--    تُنتج صفوفاً مكررة (أُثبت معملياً: ثلاث عمليات إدراج ⇒ 3 صفوف بدل 1).
--    الحل: فهرس فريد جزئي على المفاتيح العامة + on conflict مُسمّى.
create unique index if not exists settings_global_key_uq
  on platform.settings (key) where entity_id is null;

insert into platform.settings (entity_id, key, value, data_type, description) values
 (null,'driver.ranking.enabled',        'true',    'boolean','إظهار ترتيب السائق بين زملائه'),
 (null,'driver.ranking.mode',           '"band"',  'string', 'band نطاق مئوي · exact ترتيب رقمي'),
 (null,'driver.ranking.show_peer_names','false',   'boolean','إظهار أسماء الزملاء'),
 (null,'driver.ranking.basis',          '"success_rate"','string','success_rate · volume · composite'),
 (null,'driver.ranking.linked_to_bonus','false',   'boolean','ربط الترتيب بالمكافأة'),
 (null,'driver.ranking.linked_to_penalty','false', 'boolean','ربط الترتيب بالجزاء')
on conflict (key) where entity_id is null do update
  set value = excluded.value,
      data_type = excluded.data_type,
      description = excluded.description;
```

> **تحقق معملي (v4):** نُفِّذ التصحيح على قاعدة `pgeos` الحيّة داخل `begin; … rollback;` — إدراجان متتاليان بنفس المفاتيح أعطيا **صفاً واحداً لكل مفتاح** بدل صفين. الهجرة صارت قابلة لإعادة التشغيل.

| المفتاح | الافتراضي | الملاحظة |
|---|---|---|
| `enabled` | `true` | يُطفأ بضغطة إن أضرّ |
| `mode` | `band` نطاق مئوي | `exact` متاح لكن غير موصى به |
| `show_peer_names` | `false` | **الإظهار يخلق احتكاكاً بين الزملاء** |
| `basis` | `success_rate` | لا `volume` — العدد يعتمد على المنطقة المسنَدة |
| `linked_to_bonus` | `false` | **يرفعه المدير العام بقرار مسجَّل** |
| `linked_to_penalty` | **`false`** | 🔴 **توصيتي: يبقى مطفأً دائماً** |

**لماذا الفصل بين المكافأة والجزاء:** المكافأة على الترتيب تدفع للتحسين. **العقوبة على الترتيب تدفع للتحايل** — لأن الترتيب نسبي، فالسائق لا يتحسّن بالضرورة بتحسين نفسه، بل بإفشال غيره أو بتزوير أرقامه.

**التجربة الموصى بها:** شهر بـ `enabled=true` و`linked_to_bonus=false` — ثم يُقاس أثره على نسبة النجاح قبل ربطه بأي مال.

## 8-4 شاشة الأرباح — **أرقام العمولة الحاكمة** (v4 · R-05 · EXEC §1.2)

**هذه الأرقام لم تكن موجودة في أي وثيقة مرجعية** (10 §3 كان يتركها «قراراً مفتوحاً»، و35 §6 N6 و§11 #9 يعرضان الشاشة بلا رقم واحد) — وهي محسومة منذ EXECUTION-MASTER §1.2 (OPS-41 · ADM-39).

| البند | **القيمة المعتمدة** | الملاحظة |
|---|---|---|
| **الأساس** | **0.300 د.ك لكل شحنة مسلَّمة** | **ثابت (FIXED)** — لا شرائح ولا تدرّج |
| **بونص الجودة** | **+0.050 د.ك** | يُستحق عند **نسبة النجاح من أول محاولة ≥ 85%** **و****صفر فرق COD في الشهر** — الشرطان معاً |
| **خصم السكن** | **23 د.ك/شهر** | بالتناسب؛ **الإعفاء بيد `GM` بسبب مسجَّل** |
| **خصم الهاتف** | **5 د.ك/شهر** | — |
| **خصم الإقامة** | **12 د.ك/شهر** | — |
| **نافذة الاعتراض** | **٤٨ ساعة** من إتاحة كشف اليوم (إشعار N6) | 40 §C7 `commission_daily` |
| **اللقطة** | `hr.commission_daily.source_snapshot` **مجمَّدة** | الأرقام لا تتغيّر بأثر رجعي بعد إتاحتها |

**العرض للسائق:** الأساس × عدد الشحنات · البونص (مع **سبب عدم الاستحقاق** إن لم يُستحق) · كل خصم **بسطر مستقل باسمه** · الصافي. **لا خصم مجمَّع بلا بيان.**

**الموضع في القاعدة:** الأساس والبونص في **`hr.commission_rules`** (+ `bonus_rate` و`bonus_condition`)، والخصومات الثلاثة **بأعمدة مستقلة** في `hr.commission_daily` (`deduction_housing` · `deduction_phone` · `deduction_residency` · `deduction_other` + `deduction_reason`) — وإلا استحال إثبات أي منها. والقيم الرقمية تُبذر في **`platform.thresholds`**: `driver.commission_base = 0.300` · `driver.commission_bonus = 0.050` · `housing.deduction = 23` · `housing.phone_deduction = 5` · `housing.residency_deduction = 12`.

**حدود `driver_trust` في هذه الشاشة (ADR-28 · EXECUTION-MASTER-v4 §1.15):**
- **لا يُعرض `driver_trust` كقيمة مركّبة للسائق إطلاقاً** — يُعرض له المكوّن القابل للتصرف وحده (مثل «محاولات الاتصال المسجَّلة») لا الرقم المجمَّع.
- **لا يُربط بأجر ولا بعمولة ولا ببونص ولا بجزاء.** استخدامه الوحيد: شرط إقفال DTL الآلي (07 §5-6) ومدخل تشغيلي للمشرف.
- وكذلك **الترتيب بين الزملاء غير مرتبط بالجزاء (`linked_to_penalty = false` · FIXED)**.

**الفصل الحاكم (v4 — OPS-35 · 40 §A4/§B5):** **الحدود العددية في `platform.thresholds`** (يحرّرها `GM` بلا نشر) · **الإعدادات السلوكية/النصية في `platform.settings`**.

```sql
-- (1) الإعدادات السلوكية — platform.settings

  on platform.settings (key) where entity_id is null;

insert into platform.settings (entity_id, key, value, data_type, description) values
```

# 13. الجهاز والعمل دون اتصال — **G-07 · نموذج الجهاز الشخصي** (v4)

**كان هذا القسم غائباً كلياً** عن الوثيقة الوحيدة لتطبيق السائق — بلا نموذج مصادقة لا يُبنى التطبيق (OPS-39).

| البند | **القيمة المعتمدة** |
|---|---|
| **نموذج الجهاز** | **شخصي** — **جهاز واحد لكل سائق** (`device → user`) |
| **التسجيل** | **OTP مرة واحدة** ثم **تحديث الرمز كل ٣٠ يوماً** مربوطاً بالجهاز |
| **جهاز جديد** | **موافقة مشرف** — لا تسجيل ذاتي |
| **نافذة العمل دون اتصال** | **٧ أيام** |
| **الطابور المحلي** | **SQLite** · كل عملية بمعرّف **UUID** فريد · الخادم يرفض المكرر بالمعرّف |
| **مفتاح توقيع الجهاز** | كل عملية في الطابور مختومة بـ**`user_id` المنفِّذ + توقيع الجهاز + توقيت العملية** |
| **قبول العملية** | تُقبل إذا كان الرمز صالحاً **وقت تنفيذ العملية** لا وقت المزامنة |
| **جهاز ملغى أو مفقود** | **إبطال فوري · طابوره يُحجر لمراجعة المشرف** · بيانات الجهاز مشفّرة محلياً |
| **بدء الوردية** | متصل (بصمة وجه)؛ وعند التعذّر عَلَم **`offline_start`** |
| **إقفال الوردية** | إنهاء الجلسة بطابور معلّق **مسموح (تسليم وردية)**؛ الإقفال يتم تلقائياً عند مزامنة آخر عملية — **ولا تُعلَّم وردية مقفلة وطابورها > ٠** |
| **ما لا يعمل دون اتصال** | **رابط الدفع** (§2-1) — النقد فقط، ويُعلَم السائق بوضوح |

**الفرق عن PDA (30 §6-1):** PDA **جهاز مشترك** · أي عامل مصرَّح · **PIN ٦ أرقام بتجزئة محلية** · **OTP أسبوعي** · **offline ٧٢ ساعة**.

**القاعدة المشتركة (40 §B1 — v4):** **لا كلمات مرور مخزَّنة على الخادم**؛ PDA يخزّن **تجزئة PIN محلياً** بعد أول دخول متصل وفق G-07.
