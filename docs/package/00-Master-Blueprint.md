# 1. هوية النظام

## 1-1 ما هو

نظام تشغيل مؤسسي واحد يدير **النشاط التجاري الكامل لمجموعة بريميوم**، عبر **خمسة كيانات قانونية**: كيان قابض واحد (`PGH`) وأربعة كيانات تشغيلية منفصلة، بإدارة محاسبية موحّدة وإدارة مبيعات موحّدة.

## 1-2 ما ليس هو

| ليس | لماذا |
|---|---|
| نظام موارد بشرية بإضافات تجارية | الموارد البشرية نطاق خادم للتشغيل، لا محوره |
| أربعة أنظمة لأربع شركات | النشاط واحد والعميل واحد؛ الفصل قانوني لا تشغيلي |
| مجموعة شاشات إدخال | كل شاشة تمثّل **عملية** لها مسار وحالات ومخرجات |
| نظام يحوي «تبويب النماذج» | النموذج مخرَج من عملية، لا مدخل لها — انظر §5 |

# 2. بنية المجموعة — الأساس الحاكم للتصميم

## 2-1 الكيانات الخمسة — قابضة وأربع تشغيلية

| الرمز | الكيان | `entity_kind` | النشاط | نوع العميل |
|---|---|---|---|---|
| **PGH** | بريميوم جروب القابضة | `holding` (الجذر — `parent_id = null`) | التكاليف المشتركة · الموظفون التنفيذيون · العقود الإطارية | **لا تفوتر عملاء خارجيين إطلاقاً** |
| **PCC** | بريميوم CC | `operating` (`parent_id = PGH`) | كول سنتر وبدالة | داخلي (عملاء المجموعة) + خارجي (كول سنتر فقط) |
| **PST** | بريميوم ستوراج | `operating` (`parent_id = PGH`) | إدارة مخازن متكاملة 2PL / 3PL | خارجي |
| **PDL** | بريميوم دليفري | `operating` (`parent_id = PGH`) | توصيل طلبات | خارجي |
| **POR** | بريميوم أوردر | `operating` (`parent_id = PGH`) | توصيل طلبات | خارجي |

**قواعد الكيان القابض (EXECUTION-MASTER-v4 §1.5 · 40 §A2 — التعريف الحاكم في `database/13B`):**

| القاعدة | التطبيق |
|---|---|
| الجذر | الأربعة التشغيلية أبناء `PGH` عبر `parent_id` |
| ما تحمله القابضة | التكاليف المشتركة · رواتب الإدارة العليا · العقود الإطارية |
| توزيع التكاليف المشتركة | شهرياً على الأربعة التشغيلية عبر `billing.cost_allocations` — الأساس الافتراضي **نسبة الإيراد** |
| منع الفوترة الخارجية | مُشغِّل `billing.reject_holding_invoice()` يرفض أي فاتورة غير بينية على `PGH` |
| دليل الحسابات | التوزيع يمرّ على الحسابين البينيين القائمين **4900 إيراد بيني** / **5900 مصروف بيني** (06 §5) ويُحذف عند التجميع |

## 2-2 القاعدة المعمارية: متعدد الكيانات (Multi-Entity)

**كل حركة مالية أو تشغيلية تحمل `entity_id` إلزامياً.** هذا ليس حقلاً إضافياً — هو المحور الذي تُبنى عليه المحاسبة.

| المستوى | ما يحدث |
|---|---|
| **العميل** | سجل واحد في CRM (`accounts`) مهما تعدّدت الكيانات التي يتعامل معها |
| **العقد** | عقد لكل كيان — لأن الالتزام القانوني على الكيان لا على المجموعة |
| **الفاتورة** | **فاتورة من الكيان المُقدِّم للخدمة حصراً** — متطلب قانوني غير قابل للتفاوض |
| **كشف الحساب** | موحّد على مستوى المجموعة (إداري) + مفصّل لكل كيان (قانوني) |
| **الحد الائتماني** | يُضبط على مستوى المجموعة، ويُستهلك من كل الكيانات — العميل المتعثّر متعثّر لدى الجميع |
| **التقارير** | مجمّعة للمجموعة · مفصّلة لكل كيان · محذوفة منها المعاملات البينية عند التجميع |

## 2-3 المعاملات البينية (Inter-Company)

**الحالة الأكثر تكراراً:** عميل تخزين لدى PST يحتاج توصيلاً → PDL تنفّذ.

| الطريقة | متى تُستخدم | المعالجة في النظام |
|---|---|---|
| **إعادة فوترة** | العقد مع PST وحدها | PDL تفوتر PST بسعر داخلي · PST تفوتر العميل بسعر العقد · الفرق هامش PST |
| **فوترة مباشرة** | العميل له عقد مع كلٍّ | كل كيان يفوتر خدمته مباشرة |
| **بدالة PCC للمجموعة** | دائماً | PCC تفوتر الكيانات الأخرى شهرياً بسعر تحويلي معتمد |

**قاعدة إلزامية:** كل معاملة بينية تُعلَّم `is_intercompany = true` وتُحذف آلياً عند تجميع حسابات المجموعة. بدون هذا يتضخّم إيراد المجموعة بأرقام وهمية.

**لا يقرأ موديول جداول موديول آخر مباشرة.** التبادل عبر عقد معلن (دالة أو عرض). المخالفة تُفشل الاختبار الآلي.

# 5. مبدأ P8 — محرّك الوثائق (لا تبويب نماذج)

## 5-1 المشكلة في النموذج القديم

تبويب «النماذج» يخلق مسار إدخال ثانياً: الموظف يفتح النموذج، يعبّئ بيانات موجودة أصلاً، فتتكرّر البيانات وتتعارض. وهو أيضاً يفصل الوثيقة عن العملية فلا يُعرف أي وثيقة صدرت عن أي حركة.

## 5-2 التصميم البديل

```
عملية → انتقال حالة → محرّك الوثائق → مستند مُولَّد + مؤرشف + مربوط بالحركة
```

| المكوّن | الوصف |
|---|---|
| `document_templates` | قالب لكل نوع مستند: HTML + الحقول + اللغة + الترويسة والتذييل من إعدادات الكيان |
| `document_bindings` | ربط: (نوع المستند) ← (العملية + انتقال الحالة الذي يولّده) |
| `documents` | كل مستند مُولَّد: رقمه · نسخته · الحركة الأصل · من ولّده · متى · ملف PDF مجمَّد |

**السلوك:** عند اعتماد أمر صرف، يُولَّد إذن الصرف تلقائياً وبرقمه، ويظهر زر «طباعة» **في شاشة الأمر نفسها**. لا يوجد في النظام مكان آخر لإصدار إذن صرف.

**استثناء واحد مسموح:** النموذج الورقي الفارغ للميدان (متقدّم بلا حساب، عمل ميداني بلا شبكة). يُطبع من القالب نفسه، وله خانة مرجع تُدخل في النظام لاحقاً. **لا يُنشئ سجلاً بذاته.**

## 5-3 الهوية البصرية

كل مستند يرث من إعدادات الكيان المُصدِر: الشعار · الاسم القانوني · السجل التجاري · الرقم الضريبي · العنوان · بيانات التواصل. **بيانات الكيان تُدخل مرة واحدة** وتظهر في كل مستند تالٍ — تغييرها ينعكس فوراً.

الخط: **Cairo** (بديل Segoe UI/Arial). المستندات ثنائية اللغة عربي/إنجليزي. الألوان: كحلي `#14284B` · نحاسي `#B5673E` · رمادي `#6B7280`.

# 6. المعمارية التقنية

## 6-1 الطبقات

```
العرض:      واجهة إدارية (SPA) · PDA (PWA) · نافذة العميل (منفصلة) · لوحات تنفيذية
              │
البوابة:     مصادقة · تحديد معدّل · تسجيل · إصدار
              │
النطاقات:    12 موديولاً — كل منها بجداوله وقواعده وعقده المعلن
              │
المشتركة:    تحقق · صلاحيات · تدقيق · ترقيم ذرّي · آلات حالات · محرّك وثائق · محرّك أحداث
              │
القاعدة:     PostgreSQL — مصدر الحقيقة الوحيد · RLS على كل جدول · هجرات مُصدَّرة
              │
الخلفية:     عمّال مجدولون · طوابير · تكاملات (iMile · أولى · ~~البصمة~~ [SUPERSEDED — ADR-0003] · واتساب · بريد)
```

| الطبقة | التقنية |

| الوصول للبيانات | Drizzle ORM — المخطط كشيفرة، هجرات مُصدَّرة |

| المصادقة | رمز لمرة واحدة بالبريد + JWT · جلسة 6 ساعات |
| المجدولة | **pg-boss** (طوابير ومهام مجدولة) — كما 40 §A4 |
| الملفات | تخزين كائنات بقواعد دورة حياة |
| الوكيل الميداني | Node + Playwright (iMile) |

## 6-3 محرّك الأحداث — العمود الفقري للفوترة

```
عملية تشغيلية تُقفل → حدث مجال (Domain Event) → مشتركون
                                                    ├─ محرّك الفوترة → billable_event
                                                    ├─ محرّك التنبيهات → إشعار
                                                    ├─ محرّك الوثائق → مستند
                                                    └─ سجل التدقيق → قيد
```

**هذا ما يضمن P10.** لا يُكتب حدث فوترة يدوياً أبداً؛ يُولَّد من إقفال عملية. وكل سطر فاتورة يُرَدّ إلى حدثه، والحدث إلى عمليته، والعملية إلى منفّذها وتاريخها.

## 8-1 قواعد التسلسل

| القاعدة | السبب |
|---|---|
| M01 و M12 أولاً بلا استثناء | لا يُبنى شيء بلا هوية وتدقيق ومحرّك أحداث |
| M03 قبل M02 | لا عرض سعر بلا كتالوج وحدود دنيا |
| M07 بعد نطاق تشغيلي واحد على الأقل | الفوترة تحتاج أحداثاً حقيقية تُفوتر عليها |
| M11 (iMile) يمكن أن يتوازى مع M05 | يستخدم بنيته لكنه مستقل — وهو أعلى عائد فوري |
| M10 أخيراً | نافذة العميل تعرض ما بُني، ولا تُبنى على فراغ |

## 8-2 تعريف «منجز» لكل موديول

لا يُعتبر موديول منجزاً إلا باكتمال الستة:

1. المخطط منشور بهجرة مُصدَّرة + RLS مفعّل
2. كل عملية لها آلة حالات معلنة ومُختبرة
3. كل عملية تولّد أحداثها ووثائقها تلقائياً
4. الصلاحيات مولَّدة من السجل، ولا دور أعمى عن جداول موديوله
5. بيانات نموذجية محمّلة وسيناريو كامل يعمل من طرف لطرف
6. اختبارات آلية تغطي: آلة الحالات · الصلاحيات · إعادة بناء الدفتر بفرق صفر

| # | القرار (كما طُرح في v1) | الحالة في v4 · القيمة المحسومة |
